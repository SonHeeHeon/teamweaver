TEAMWEAVER · C1 · 2026-10-04

실패 기록을 바로잡고,
아주 작은 숫자 오차도 안전하게 다루기

설계·구현 계획 작성 / 제품 구현 전

다음은 C1이 맞습니다. 다만 “실패를 통과로 바꾸기”가 아니라, 왜 실패했는지 정확히 보여주고 실제 조건을 만족하는 결과만 반환하기가 목표입니다.

이 문서는 기술자가 아닌 프로젝트 의사결정자를 위한 설명입니다. 모든 인력·실험 데이터는 가상이며 실제 조직의 성과를 입증하지 않습니다.

1. C0 다음에 C1이 필요한 이유

솔버는 “누구를 어느 프로젝트에 몇 % 투입하면 계산 점수가 가장 좋아지는가?”를 푸는 계산 엔진입니다. C0는 계산 엔진의 답을 그대로 믿지 않고, 다른 코드가 예산·시간·인원 규칙을 다시 검사하는 안전 관문을 달았습니다.

그 관문이 예산을 아주 조금 넘은 답을 발견했습니다. 예산이 2046인데 재계산 비용이 2046.0000025인 사례입니다. 차이는 작지만 현재 검사 기준 0.000001보다 큽니다. 실제 비용 단위를 아직 모르므로 이를 “몇 원”이라고 부르면 안 됩니다.

C0 체크포인트의 전체 테스트: 539 통과 / 6 실패 / 10 제외. 기본 시연 데이터의 사전 계산도 거절됩니다. 이 문제가 해결되기 전에는 C0를 main에 합치면 안 됩니다. 이번 문서 작업에서 새로 전체 테스트를 실행한 수치는 아닙니다.

2. 과거 실험에서 무엇이 빠졌나?

일부 실패 이유가 결과의 안쪽 칸인 payload.error에 있었습니다. 보고서는 바깥 칸과 일부 검사 기록만 읽어서, 검증 때문에 거절된 87건을 놓쳤습니다. 종이 두 장 중 첫 장만 보고 뒷장의 경고를 빠뜨린 것과 비슷합니다.

원시 해는 화면용으로 줄이기 전의 자세한 숫자표입니다. 이 표가 없으므로 예산 거절 86건이 모두 작은 반올림 오차였다고 말할 수 없습니다. 새로 풀어보는 것은 재현 실험이지, 당시 숫자표를 되찾는 일이 아닙니다.

이번에는 원본 357건을 기존 해시 검사로 읽었습니다. 해시는 파일이 바뀌었는지 확인하는 지문 같은 값입니다. 원본 상태는 완료 197, 유효 후보 없음 87, 시간 초과 68, 감독자가 완료를 확인하지 못한 중단 5건이며 파일은 바꾸지 않았습니다.

3. 비교의 분모도 나눠야 합니다

실전 비교용 본평가·재확인은 솔버마다 108건입니다. 여기에 예비 실험 3건과 설치 호환성 1건을 섞으면 112건이 됩니다. 목적이 다른 시험은 별도 표로 보여주겠습니다.

원본 v2 기록의 단계별 재집계입니다. 같은 입력의 반복 측정도 포함돼 108개의 독립 고객 사례를 뜻하지 않습니다. 완료는 5% 품질 증명과 다르며 CBC는 신뢰할 상한이 없어 품질 증명 상태를 따로 표시해야 합니다.

끝난 사례의 평균·중앙 속도만 보면 어려워서 실패한 사례가 빠집니다. 이를 “생존 편향”이라고 합니다. 새 보고서는 실패와 중단도 분모에 남기고, 완료·검증 통과·품질 통과를 따로 보여줍니다.

4. 해결 기술은 세 후보를 비교합니다

방법쉬운 설명선택 판단
A · 검사 기준 완화“조금 넘어도 괜찮다”고 바꾸기실제 초과를 숨길 위험. 기본안으로 택하지 않음
B · 출력 정밀도 개선계산기가 숫자를 더 자세히 전달하게 하기설치 CBC에서 가능한지, 어디서 값이 줄었는지 먼저 확인
C · 투입률 미세 재계산사람은 그대로 두고 소수점만 아주 조금 조정잠정 권고. 실제 재검증·시간 기준 통과 후 연결

C에는 프로젝트가 이미 쓰는 무료 오픈소스 SciPy의 HiGHS 선형계획 기능을 활용합니다. 선형계획은 여기서 “누구를 선택했는지는 바꾸지 않고 투입률 숫자만 계산하기”입니다. 새 상용 라이선스나 패키지 추가는 필요하지 않지만 추가 계산 시간과 유지보수 비용은 생깁니다.

이 기능은 연속 변수의 경계와 부등식, 시간 제한을 지원합니다. 실제 설치 버전에서 지원 여부를 확인하겠습니다. SciPy 공식 문서

C는 확정 구현이 아니라 파일럿으로 검증할 설계 제안입니다. 통과하지 못하면 보고서 정정만 완료하고 서비스 연결은 보류합니다. 통과시키려고 기준을 넓히지 않습니다.

5. 미세 복구는 만능 수정기가 아닙니다

제안 가드레일은 예산 대비 오차 비율 최대 1e-7, 투입률 변화 최대 1e-7, 추가 복구 시간 최대 2초의 목표입니다. 50% 투입을 60%로 바꾸는 개선이 아니라 0.50000000 근처의 아주 작은 차이만 다룹니다. 이 수치는 실제 인사팀이 승인한 허용치가 아닙니다.

기존 최종 검사 기준 1e-6은 그대로 둡니다. 예산뿐 아니라 가용률·추가 제약도 원래대로 만족해야 합니다. 선택값이 0.75이거나 숫자가 없거나 무한대인 답을 0/1로 억지로 바꿔 살리지 않습니다. 복구가 실패하면 거절합니다.

수정 전 원본, 검사에 넣은 후보, 최종 답을 따로 저장하고 점수·오차·시간도 전후로 기록합니다. 과거 87건의 실패 파일을 새로 만든 것처럼 채우지 않습니다.

6. 개발은 다섯 체크포인트로 진행합니다

보고서부터 정정

누락된 오류와 핵심 108건의 분모를 고칩니다. 과거 실패는 실패로 남기며 원본 파일과 과거 보고서는 보존합니다.

원인과 A/B/C 후보를 계측

실패 입력을 제한 재현해 숫자가 어디서 달라지는지, 정밀 출력이 가능한지, 변경 비용과 시간을 비교합니다.

서비스에 연결하지 않은 복구기 검증

미세 재계산 기능을 만들고 일부러 잘못된 답·시간 초과·추가 제약을 넣어 검사가 잡는지 확인합니다. 파일럿 판정에 통과해야 다음 단계로 갑니다.

세 솔버와 증거 저장 연결

CBC·HiGHS·SCIP 모두 같은 규칙을 적용합니다. 성공뿐 아니라 실패 원본과 파일 지문도 저장합니다.

서비스 회귀와 제한 재비교

기존 실패 6건, 전체 테스트, 작은 정답 대조, 기본 사전 계산을 확인합니다. 새 기록으로 제한된 3솔버 비교를 하고 독립 리뷰를 받습니다.

각 체크포인트에 커밋·리뷰·지표·쉬운 HTML 설명을 남깁니다. 이번에는 이 설계와 계획을 작성했으며 위 구현 단계는 아직 시작하지 않았습니다. 24시간 전체 재실험도 자동으로 시작하지 않습니다.

7. “최적”과 “공정한 비교”의 한계

복구 LP가 자기 문제의 최적 답을 찾았다고 전체 인력 배치가 최적이라는 뜻은 아닙니다. 사람 선택은 이미 고정했기 때문입니다. 신뢰할 상한은 “이 점수 이상은 불가능”이라는 증거입니다. 상한이 없는 CBC에 임의로 만들어 붙이지 않습니다.

C를 쓰면 CBC에도 보조 HiGHS 계산이 들어갑니다. 그래서 원래 솔버 자체 성능과 솔버+복구의 최종 성능을 따로 보고해야 합니다. 과거 v2와 새 정책의 결과를 한 덩어리로 섞지 않습니다.

실험의 최대 240초 기한은 늘리지 않습니다. 복구는 기존 검사·저장용 여유 안에서 진행합니다. 서비스의 2초 추가 목표는 프로세스를 강제로 끊는 보장이 아니며 실제 총 응답시간을 절대 보장하지 않습니다.

C1이 통과해도 대안 중복·빈 결과(C2), 표시 투입률의 반올림 문제(C3), 데이터 보관 경로(C4), 상용 비교(C5), 실제 배치 규칙(C6)은 남습니다. 실제 성과 검증은 인사/프로젝트 성과 데이터가 별도로 확보돼야 가능합니다.

8. 이번 산출물과 다음 행동

이번 작업: C1 설계 문서, 단계별 구현 계획, 독립 설계 리뷰, 이 HTML입니다. 제품 코드는 바꾸지 않았고 기존 C0 회귀가 해결됐다고 주장하지 않습니다.

독립 설계 리뷰: PASS. 최고 역량 모델 gpt-6-astra가 별도 세션에서 검토했습니다. 정규화 전·후 후보 구분과 추가 제약 보존 등 지적 4건을 반영했습니다. 구현 성공·main 통합 승인은 아직 아닙니다.

다음 행동: 설계를 확인한 뒤 계획을 승인하면 1번 보고서 정정부터 구현합니다. 복구 연결은 파일럿 통과 후입니다. main 병합과 원격 push는 별도 승인이 필요합니다.
