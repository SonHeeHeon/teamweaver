P0 · 해의 유효성 / 최우선

검증되지 않은 CBC 해를 유효한 배치처럼 반환할 수 있음

현재 CBC 코드는 변수에 숫자가 들어 있기만 하면 “해가 있다”고 판단합니다. 시간 제한 0초를 준 재현에서 솔버는 Not Solved였지만 변수에 분수 값(z=0.75)이 남았습니다. 이 값은 사람을 0.75명 뽑는다는 뜻이 아니라, 정수 조건을 풀기 전의 중간 계산입니다. 그럼에도 현재 솔버 함수는 한 명을 뽑은 듯한 계획을 만들고 미충원과 위반을 비워 반환했습니다. 별도의 독립 검증기는 같은 결과를 이진 조건 위반으로 거절했습니다.

재현: time_limit=0, 중급 2명 필요, 예산 제약. 상태 Not Solved, z=[1.0, 0.75], 계획에는 1명, 독립검증은 binary_domain 실패. 함수가 반환 전에 독립 검증을 강제하지 않는 것이 핵심.

조치: 모든 솔버가 반환하기 전 공통 검증기를 반드시 통과하게 하고, incumbent(제한 시간 안에 발견한 정수 해)가 없으면 추천을 반환하지 마세요. 0초·초단기·중단·분수 변수 테스트를 추가하세요.

P0 · 수치 검증 / 실험 비교에 직접 영향

CBC 결과 85건이 수치 허용오차 때문에 탈락했는데, 원인이 보고서에서 사라짐

원본 Phase 1 체크포인트 357건을 확인했습니다. 87건은 “쓸 수 있는 해 없음” 상태입니다. 그중 CBC 85건과 HiGHS 1건은 예산 제약의 검증 허용오차 위반, CBC 1건은 이진 변수 위반으로 거절됐습니다. 대부분은 솔버가 불가능 판정을 내린 게 아니라 결과가 현재의 엄격한 검증 기준을 통과하지 못한 것입니다. 그런데 결과 HTML은 검증 실패 0건을 표시하고, 실패 사유도 빈칸으로 보일 수 있습니다. 이 때문에 사용자는 실패가 없었다거나 솔버가 단순히 느렸다고 오해할 수 있습니다.

원본 대조: `phase1-long-sweep-v2/checkpoint.json`의 357 상태와 각 `result.json`의 payload.error. 합계: CBC budget 85 + CBC binary_domain 1 + HiGHS budget 1. HTML 생성기 `experiments/phase1/report.py`는 검증 실패를 payload.validation 또는 특정 checkpoint status에서만 세며, 표 오류 칸은 바깥쪽 result.error만 확인합니다. 이 87건은 안쪽 payload.error에 있습니다.

조치: 생성기에서 실패 상태와 payload.error를 집계·표시하고, “솔버 실패”, “해는 있으나 검증 실패”, “시간 초과”, “품질 한도 미달”을 따로 나누세요. 그 다음 상대·절대 허용오차, 입력 단위(원/천원 등), 반올림 순서를 모델 정의와 맞춰 재실험하세요. 검증을 느슨하게 풀어 통과율을 올리기 전에 실제 위반 규모부터 계측해야 합니다.

P1 · 설명의 사실성 / 사람에 대한 정보

“리뷰 근거 문장” 자리에 실제 리뷰가 아닌 숫자를 넣음

교체 설명에 전달되는 evidence는 리뷰 문장 대신 감정 점수 숫자입니다. SQLite 조회가 reviewer_id와 text_polarity만 반환하고, 원문 리뷰 텍스트는 저장하지 않습니다. 반면 테스트 이름은 “실제 리뷰 문장”을 주장하지만 단지 evidence 목록이 비어 있지 않은지만 확인합니다. 사용자가 자연어 근거를 믿으면 숫자를 인용문으로 착각하거나, 모델이 원문에 없는 문장을 만든 것으로 오해할 수 있습니다.

확인: core/rag/sqlite_rag.py:27–28가 key=리뷰어 ID, value=polarity 숫자를 선택. tests/api/test_rag_context.py:29–39는 값 존재만 검사. 리뷰 원문과 추출 문장 간 일치 여부는 평가하지 않음.

조치: 원문 문장 또는 검증 가능한 문장 ID·출처를 보존하고 인용 범위를 제한하세요. 테스트가 “원문에 포함된 정확한 인용인지” 검사하도록 바꾸세요. 원문이 없다면 수치를 의견 근거처럼 포장하지 말고 “수치 요약”으로 표시하세요.

P1 · 보안 / 배포 전 차단

PDF 생성기가 요청의 Host를 믿고 그 주소로 브라우저를 보냄

PDF API는 들어온 요청의 Host 값을 바탕으로 서버 내부 브라우저가 접속할 주소를 정합니다. 외부에서 API에 접근할 수 있고 Host를 제어할 수 있다면, 악성 Host로 서버의 브라우저를 다른 주소로 유도할 가능성이 있습니다. PDF 데이터가 브라우저 페이지에 들어가므로 데이터 유출 위험도 생깁니다. 이번 검수에서는 네트워크 접속이나 공격 실행은 하지 않고 코드 흐름만 확인했습니다.

조치: 고정된 내부 origin/허용목록을 사용하고 임의 Host를 거절하세요. 브라우저의 로컬 접근도 제한하고, 인증·요청 크기·동시 실행 한도를 더하세요. 외부 서비스로 공개하기 전에 보안 검토가 필요합니다.

P1 · 추천 신뢰도

“대안 팀” 생성이 중복 또는 지나치게 나쁜 후보를 반환할 수 있음

한 사람만 가능한 팀에 22명 정원을 요구하는 예제에서는 대안 B·C·D가 모두 빈 팀으로 반복됐고, 각각 같은 점수와 22명 미충원을 가졌습니다. 대안 생성은 이전 팀과 달라졌는지만 찾고, 실질적으로 다른 후보인지·품질이 기준에 맞는지 확인하지 않습니다. 화면에 A/B/C/D가 있다고 네 가지 유의미한 선택지가 있는 것은 아닙니다.

조치: 팀 구성을 정규화한 서명으로 중복 제거, 빈 계획 제외/표시, 최소 품질·미충원 한도를 적용하고, 후보가 부족하면 “대안 없음”을 명시하세요.

P1 · 일정 정확성

요구에 적히지 않은 직급의 사람도 정원 밖에서 뽑힐 수 있음

모델은 입력에 지정된 직급별 정원만 채우게 하고, 정원에 언급되지 않은 다른 직급은 0명으로 묶지 않습니다. 중급 1명만 요청한 작은 예제에서 중급 1명과 주니어 1명이 모두 선택됐습니다. 비즈니스 의도가 “허용된 직급만 정확히 선발”이라면 실제 조합이 잘못됩니다.

조치: 직급이 생략되면 0명으로 볼지, 자유 인원으로 볼지 계약을 정하고, 사람 수 정합성 테스트를 추가하세요.

P2 · what-if

교체 후 점수가 전체 최적화 점수와 같지 않음

교체 계산은 기술 차이와 협업 점수를 단순 합산합니다. MILP의 시너지 가중치(람다), 과친숙 페널티, 정원·예산·가용성 제약과 일부 가지치기 규칙을 모두 반영하지 않습니다. 또 교체로 정원·예산·가용성이 깨지는지 검증하지 않습니다. 이를 “모델 점수 변화”나 전체 목적함수 차이로 표시하면 잘못된 비교입니다.

조치: 전체 모델을 고정한 재최적화를 하거나, 가벼운 근사치라면 화면과 API에서 “부분 점수 추정”이라 이름 붙이고 제약 통과 여부를 별도 계산하세요.

P2 · 숫자 표기와 검증 일치

0.206 배정을 화면에서 0.21로 올려 표시할 수 있음

모델은 0.206을 허용했지만 화면 변환에서 최소 배정량을 소수 둘째 자리로 반올림해 0.21로 표시하는 재현이 통과했습니다. 가용 시간이 0.206이면 화면에는 더 많은 일을 배정한 것처럼 나타납니다. Greedy 기준안도 동일한 반올림 문제가 재현됐습니다.

조치: 화면용 배정을 항상 내림하고, 표시된 최종 계획 자체를 예산·가용성으로 다시 검증하세요. API 입력에서 소수 자릿수 제한 또는 단위 계약을 명확히 하세요.

P2 · 실험 해석

112건의 비교 표에는 서로 다른 제한 시간이 섞여 있음

각 솔버당 오라클을 뺀 112건은 240초 조건만 모은 집합이 아닙니다. 체크포인트에 있는 112건은 240초 장기 실행 108건(기본 실험+확인 실험)에 호환성 1건(60초)과 사전 파일럿 3건(각 120초)을 더한 것입니다. 설명 일부가 112건 전체를 같은 240초 조건으로 묶어 읽히게 합니다. 기준 표본은 계획상 사전 파일럿 제외가 원칙입니다.

조치: 핵심 비교(108건/솔버), 파일럿(3건), 호환성(1건)을 별도 표·분모로 나누세요. 성공률과 중앙시간은 단계·크기·시나리오를 함께 공개하세요.

P2 · 그래프 검색

특정 큰 그래프에서 협업 경로를 놓칠 수 있음

메모리 그래프의 N-hop 탐색은 도달 노드 수를 8비트 정수로 누적합니다. 128개 연결 경로를 한꺼번에 세는 작은 재현에서 중간 메모리 탐색은 목적지 1개를 놓쳤고 SQLite 결과에는 있었습니다. 고밀도 그래프에서 추천 근거/맥락 조회가 달라질 수 있습니다.

조치: 더 넓은 정수형 또는 논리 OR 탐색을 쓰고, 밀도·노드 수 경계 테스트를 추가하세요.

빌드된 Python wheel에는 데모에 필요한 입력 파일·화면이 없음

완료 기록은 357건입니다. 여기에는 작은 오라클 21건과 비오라클 비교 336건(각 솔버 112건)이 들어갑니다. 비오라클에서 본문에 보고된 성공은 HiGHS 79/112, SCIP 75/112, CBC 22/112입니다. 하지만 CBC의 추가 86건·HiGHS 1건은 예산 제약 검증에 실패했으므로, 표의 성공률은 “솔버가 해를 찾은 비율”만이 아니라 “현재 검증 기준까지 통과한 비율”입니다. 검증 오차 원인을 바로잡기 전에는 솔버 엔진 성능 차이라고 단정하지 마세요.

독립 리뷰와 남은 한계

리뷰 절차 준수: 부분 충족·명시

전역 규칙에 따라 가장 높은 역량으로 지정된 gpt-6-astra 모델로 서로 다른 범위를 독립 검토하도록 세 명의 리뷰어를 요청했습니다. 각 리뷰어는 핵심 예비 발견을 전달했지만, 최종 답변을 완료하기 전에 사용량 제한으로 작업이 종료됐습니다. 그래서 최고 모델 리뷰를 완전히 완료했다고 주장하지 않습니다. 받은 발견은 제가 원본 코드·fixture·결과 JSON·테스트 실행으로 직접 다시 확인했습니다. 이 최종 종합은 활성 환경의 기본 Codex 모델로 수행했으며, 높은 모델 리뷰가 끝나지 않은 잔여 위험이 있습니다.

확인된 예비 독립 리뷰 주제는 계산/데이터/최적화, 앱/API/보안/운영, 실험/보고 방법론이었습니다. 본 보고서에서 재현한 결과를 우선 채택했고, 아직 코드 흐름만 본 보안 항목은 가능성으로 표현했습니다. 리뷰어의 사용량 제한 때문에 모든 발견을 독립적으로 끝까지 교차검증하지 못했습니다.

검수는 설계·구현·기록을 다각도로 읽은 중간 점검이지, 개인정보 영향평가, 법률 검토, 침투 테스트, 인사 공정성 인증은 아닙니다. 실제 인력·리뷰 데이터가 없으므로 모델의 편향/현실 타당도는 이번 자료로 판정할 수 없습니다.

지금 기억하면 좋은 세 문장

1. 현재 추천은 실제 조직에서 잘 작동한다고 검증된 추천이 아닙니다.

2. 실험의 87개 거절을 모두 “솔버가 못 품”이라고 읽으면 안 됩니다. 검증 허용오차 문제가 대부분입니다.

3. 가장 먼저 해의 검증을 모든 반환 경로에 강제하고, 실패를 정직하게 보고하도록 고친 뒤 다시 비교해야 합니다.
