03모델은 무엇이고, 솔버는 무엇인가

모델 = 선택 규칙

무엇을 좋은 배치라고 할지, 무엇을 지켜야 할지 방정식으로 적은 것입니다. 요리의 조리법에 해당합니다.

솔버 = 계산하는 도구

그 방정식을 풀어 조합을 찾는 프로그램입니다. 같은 조리법을 실행하는 다른 조리 도구에 해당합니다. 서비스는 HiGHS 하나로 고정했습니다.

솔버를 바꾸는 것과 방정식을 바꾸는 것은 다른 일입니다. 방정식을 바꾸면 좋은 배치의 정의가 바뀌므로 다시 검증해야 합니다. 그래서 이 저장소에는 방정식을 다시 쓰는 곳 다섯 군데(서비스 MILP, 벤치 정식, 예산 보정 LP, 독립 검증기, 평가기)를 함께 고치고 Phase 0 검증을 다시 돌리는 규칙이 있습니다.

12지식 그래프와 기술 이름 사전 (10월 8~9일)

지식 그래프는 “사람—기술—사업—고객사—산업—평가—협업”을 점과 선으로 이은 지도입니다. 8월에 Neo4j(그래프 전용 DB)를 뺀 것은 검색 속도·저장 근거가 없어서였습니다. 이번에 다시 그래프를 만든 이유는 다릅니다. 인사팀 소명 글과 조직 기술 지도처럼 여러 종류의 사실을 한 번에 엮어 보여 주는 용도가 생겼기 때문입니다.

그래프 하나, 보기 둘

“용도별로 각각 만들어야 하나?”라는 질문에 그래프는 하나만 만들었습니다(core/kg). 보기는 두 가지입니다. ① 조직 기술 지도: 어떤 기술이 몇 명에게 얼마나 있고, 신규 제안에 무엇이 모자란지. ② 사업별 근거: 요구 기술 충족, 같은 산업·고객사 경험, 팀 안 협업 이력, 동료 평가, “왜 다른 사람이 아니었나”(현행 평가기로 잰 교체 비교). 실데이터에서는 이름·평가 원문·업무 요약을 그래프에 넣지 않습니다.

실제 기술 이력은 사람이 직접 적은 이름이라 같은 기술이 여러 이름으로 들어옵니다. 사용자 결정(10-09)으로 SI 핵심 기술 228개를 큐레이션한 사전을 입력 단계 기본값으로 넣었습니다. 한·영 별칭, 버전 표기(“Java 17”), 괄호 병기를 대표 이름으로 바꾸고, 상위·관련 관계를 둡니다. 하위 기술 경력은 깊이마다 70%씩 상위 기술에 인정합니다(0.7^깊이, 10-11 사용자 결정 “70%로 고정”, 이전 0.5 · 근거 없는 가정값). 사전에 없는 이름은 합치지 않고 경고만 합니다.

측정: 이름만 흐트러뜨린 사본에서 사전을 쓰면 S가 원본과 같았습니다(100·200·300명). 사전이 없으면 100명에서 사람-사업 쌍의 86%에서 S가 달라지고, 배치 점수가 57.8에서 49.1로 떨어졌습니다. 즉 실제 자료에서는 이름 정리가 배치 품질을 크게 좌우할 수 있습니다.

대안 품질은 alt ≥ A − 0.05 × |A|로 검사합니다. 10-05부터는 빈 팀·중복 구성·A보다 빈자리가 많은 후보도 뺍니다(C2). 조건을 만족하는 대안이 없으면 화면에 “조건을 만족하는 대안 없음”이 나옵니다. A안이 전역 최적이라는 독립 증명이 없으면 대안의 진짜 최적값 대비 95% 보장도 없습니다.

현실 자료 없이 만드는 가상 성과의 올바른 역할

데이터 연결과 평가 계산이 작동하는지 확인할 수 있습니다. 예를 들어 고객 점수·교체·후속 과제를 서로 다르게 생성하고 누락·지연·난도 교란을 넣어 모델이 엉뚱한 지름길을 배우는지 시험할 수 있습니다. 결과 이름에는 SYNTHETIC_TEST_ONLY를 붙이고 현실 효과의 결론을 내리지 않습니다.

현실 결과 접근이 계속 불가능하다면 서비스는 가용률·예산·합의한 선호를 계산해 의사결정을 돕는 도구로 제공할 수 있습니다. “성과가 가장 좋은 팀을 예측한다”는 약속은 범위에서 빼야 합니다. HR팀이 자기 환경에서 평가를 실행하고 승인된 집계만 전달하는 방식은 향후 협의 가능한 대안입니다. 접근 권한이나 협의가 이미 있다고 가정하지 않습니다.

20용어 사전과 지금 준비할 것

PoC / 시제품
아이디어가 동작하는지 보여주는 구현. 운영에 필요한 권한·배포·실데이터 검증까지 모두 끝났다는 뜻은 아닙니다.
MILP
정수 선택과 연속량을 함께 계산하는 최적화. “넣을까 0/1”과 “몇 % 투입할까”를 함께 정합니다.
제약 / 목적함수
제약은 예산 같은 지켜야 할 선, 목적함수는 그 선 안에서 더 좋은 답을 고르는 점수표입니다.
HiGHS / 시드 포트폴리오
서비스가 쓰는 오픈소스 솔버 / 같은 문제를 난수 시작값만 바꿔 여러 개 동시에 풀고 가장 좋은 답을 고르는 방법(서비스 4개).
LP relaxation / 완화 문제
0/1 선택을 0~1 중간값도 허용해 더 쉽게 풀어 얻는 상한. 현실에서 그대로 실행할 수 없는 분수 선택이 들어갈 수 있습니다.
incumbent / 현재 유효 후보
지금까지 찾은 실행 가능한 정수 배치. 존재한다고 최적임이 증명된 것은 아닙니다. 화면의 “시간 한도 도달(최선 증명 전)”이 이 상태입니다.
bound / gap
아직 가능할 수 있는 최고 점수의 상한과 현재 후보의 차이. 같은 방정식 기준의 계산 품질입니다.
독립 검증기
솔버의 답을 솔버 코드와 따로 다시 계산해 모든 제약과 점수를 확인하는 프로그램. 통과한 답만 화면에 나갑니다.
oracle / 소형 정답기
작은 입력의 모든 선택을 조사해 제품 계산 결과와 비교하는 별도 계산 절차입니다.
pair pruning / 관계 쌍 절삭
모든 두 사람 관계를 다 계산하면 커지므로 일부 시너지 쌍만 남깁니다. 서비스는 상위 200쌍만 보상합니다.
익숙한 쌍
최근 36개월 중 12개월 이상 같은 사업에 있던 두 사람. 같은 팀에 다시 넣으면 작은 감점을 받습니다.
연초 계획 / 운영 중 편성 / K
백지에서 6개월을 짜는 것 / 이미 배치된 조직에서 신규 제안·보강을 위해 일부만 바꾸는 것 / 운영 중 편성에서 옮겨도 되는 기존 인원 수.
미리 계산
오래 걸리는 시연 결과를 미리 풀어 둔 파일. 데이터·설정·재채점이 모두 맞을 때만 쓰고, 화면에 그 사실을 표시합니다.
CSV 묶음 / 검증 리포트
여러 CSV와 설명서(manifest)를 한 폴더·zip으로 묶은 입력 / 읽을 때 오류·경고를 파일·줄·칸까지 적은 보고서.
대리 레벨
실제 자료에 숙련도 레벨이 없어 경력 개월(12/36/60/96개월 경계)로 대신 만든 1~5 레벨. 현장 숙련도가 아닙니다.
기술 이름 사전 / 부분 인정
같은 기술의 여러 이름을 대표 이름 하나로 바꾸는 목록(228개) / 하위 기술 경력의 일부(깊이마다 70%)를 상위 기술 경력으로 쳐 주는 규칙. 계수는 가정값이고, 인정으로 생긴 경력은 본인 경력과 따로 표시합니다.
지식 그래프
사람·기술·사업·고객사·산업·평가·협업을 점과 선으로 이은 지도. 이 프로젝트는 별도 DB 없이 메모리에 만듭니다.
RAG / GraphRAG / XAI
관련 근거를 먼저 검색해 설명에 넣는 방식 / 그 근거를 지식 그래프의 사실로 주는 방식 / 왜 그런 판단인지 이해할 수 있게 보여주는 기능. 설명이 그럴듯하다고 효과가 입증된 것은 아닙니다.
자리표시 + 허용 목록
소명 글에서 AI는 사실 번호 {F12}와 정해진 연결 말만 쓰고, 숫자·판정은 서버가 데이터 그대로 채우는 방식. 목록 밖 말이 한 글자라도 섞이면 글 전체를 버립니다.
불리한 사실 덧붙임
AI 글이 빠뜨린 미달·위반·부정 평가 같은 사실을 서버가 글 끝에 사람별 줄로 붙이는 것. AI가 쓴 부분은 바꾸지 않습니다.
사전 등록 / 보류 집합
측정 전에 판정 기준을 커밋해 두는 것 / 설계를 고칠 때 보지 않은 데이터로 따로 채점해 점수가 부푸는 것을 막는 것(E7c의 “처음 보는 데이터”).
사내 LLM 대리
회사 안에 둘 AI를 대신해 잰 모델. 사내 서버로는 잴 수 없어 Z.ai 공식 API의 GLM(10-11부터 GLM-5.3-Flash)을 사내 AI로 가정했습니다. 서비스 기본은 외부 AI입니다.
직설형 평가자 / 어긋난 글
시연 평가 글에서 돌려 말하지 않고 부정을 그대로 쓰는 평가자(8%) / 고른 평가 항목과 글의 온도가 다른 리뷰(5%). 실제 회사처럼 AI 판정을 시험하려고 넣었습니다.
