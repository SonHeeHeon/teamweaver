1. 과제 개요

1.1 배경과 문제

SI 조직에서는 한 사람이 여러 사업에 걸쳐 일한다. 배치를 정하려면 기술 적합만이 아니라 사람마다 달마다 남은 시간(가용률), 사업의 등급별 정원과 월 예산, 함께 일해 본 동료(협업 이력)를 동시에 맞춰야 한다. 한 조건을 맞추면 다른 조건이 깨지기 쉬워, 담당자의 수작업 배치로는 ① 조건 위반 여부, ② 더 나은 배치가 있었는지, ③ 인사팀에 "왜 이 팀인가"를 설명할 근거를 확인하기 어렵다. 상황은 셋이다 — 가장 잦은 신규 사업 편성(대부분 이미 일하는 중, 쉬는·끝나 가는 사람과 몇 명만 옮겨 새 사업 팀을 짬), 진행 사업에 이슈가 생긴 긴급 투입, 드문 연간 계획(백지에서 6개월 배치).

1.3 범위와 전제

  • PoC·과제 제출용이다. 실제 인사 자료는 적재하지 않았다(적재 불가). 입력 형식은 실제 인사 자료의 항목과 규칙을 받아 설계했고, 개발·검증·시연은 같은 형식의 가상 데이터로 했다.
  • 점수의 계수(협업 0.3·익숙한 사이 감점 0.2·하위 기술 인정 70% 등)는 설계값이다. 결과를 맞추려고 데이터 생성기나 계수를 조정하지 않았고, 실패·중단도 기록에 남겼다.

4. 정성적 성과

  • 계산 결과를 얼마나 믿어도 되는지 함께 보여 준다. 모든 결과에 "독립 검증 통과", "최선 증명" 또는 "최적값이 이 해보다 최대 몇 % 높을 수 있음", "시간 한도 도달·사용자가 멈춤·기록에서 불러옴"을 붙이고, 교체 점수는 "참고값 · 재최적화 아님"으로 밝힌다. PDF의 이 문구도 서버 서명이 맞을 때만 찍힌다.
  • 생성형 AI를 "검사받는 부품"으로 썼다. 결정은 수학 최적화가, 읽기와 쓰기는 AI가 맡는다는 경계를 실험으로 정했다 — LLM 직접 배치(3.3)는 규모가 커지면 무너지고, 평가 글 판정(3.4)은 규칙으로는 안 된다. AI의 글은 기계 검사를 통과해야 나간다: 소명 글은 AI가 사실 번호와 연결 말만 고르고 숫자·사실 문구는 서버가 채우며, 교체 설명은 인용을 원문과 한 글자씩 대조하고 출처·보류 결론을 확인한다. 검사에 걸리면 규칙 기반 글로 대신한다.
  • 규칙을 측정으로 정했다. 보상 쌍 수·익숙한 쌍 기준·감점 방식·솔버·소명 글 방식을 대안과 같은 데이터로 비교하고, 판정 기준을 측정 전에 커밋했다(7장).
  • 측정한 대로 보고한다. 사업 효과는 NOT_CALIBRATED로 표시하고, 가상 성과로 효과를 "입증"하는 것은 순환 검증이라 하지 않았다. 대안 C가 A보다 조금 높은 것처럼 직관에 어긋나는 결과도 그대로 둔다.
  • 실제 도입을 염두에 둔 설계. 실제 인사 자료와 같은 입력 계약·검증 리포트, 평가 원문을 화면·AI에 보내지 않고 항목 라벨만 쓰는 비공개 모드, 외부 AI 차단 규칙, 사내 LLM 전환 시 차이 측정(3.5).
  • AI로 개발 과정 자체를 운영했다. Claude 두 계정과 Codex가 파일 소유 영역을 나눠 병행 개발하고(작업 분담표·인수인계 기록), 코드 변경은 커밋 전에 독립 리뷰(주로 Codex)를 받았다. 리뷰 지적은 고치기 전 코드에서 실패하는 시험으로 먼저 고정하고, 측정은 판정 기준을 먼저 커밋한 뒤 돌렸다 — 11주 동안 커밋 480여 개, 시험 1,962개.
  • 쓰는 사람의 시간을 아낀다. 안 A부터 먼저 보여 주고, 오래 걸리면 멈춰 그때까지의 가장 좋은 배치로 끝낼 수 있다. 운영 중에는 "몇 명만 옮기면 얼마나 좋아지나"를 표 하나로, 인사팀 소명 글은 근거와 함께 자동으로 낸다.

  • 자원 보호: 새 계산은 동시 2개(초과 시 429), 시간 한도 상한 900초, 요청 본문 2 MiB. 화면 연결이 끊기면 시드 프로세스까지 즉시 정리한다. PDF 브라우저는 서버 자기 주소만 열고 외부 요청을 막는다.

6. 주요 적용 기술

6.1 배치 최적화 모델 (혼합정수계획, MILP)

목적(최대화)Σi,j Sij·zij + λ·Σ(p,q)∈P, j Cpq·ypqj − μ·Σ(p,q)∈F, j ypqj − 100·Σj,g slackjg   (λ = 0.3, μ = 0.2)
전일 투입 자격zij = 0  (사업 j 기간 중 가용률im < 1인 달이 있으면 — 육아휴직 등)
프로젝트 동시 수행Σj: m∈j zij ≤ 동시 수행 상한i  (달 m마다. 기본 1, 부서장이 사유와 함께 허용한 사람만 2)
월 예산Σi 단가i·zij ≤ 예산j  (동시 수행자는 사업마다 전액)
등급 정원Σi∈g zij + slackjg = 요구 인원jg  (사업에 적힌 등급 g만)
쌍 선형화ypqj ≤ zpj,  ypqj ≤ zqj,  ypqj ≥ zpj + zqj − 1
  • 변수: z 배치 여부(0/1) — 전일 투입(서비스 기본)이라 투입률 변수가 없다. y 두 사람이 같은 사업에 있는지(곱의 선형화), slack 등급 정원 미충원(큰 감점, 결과에 노출). 예전 투입률 나누기 방식(0.3~1.0, 최대 3개 사업)은 설정에 남겼다. 시간 한도 전에 탐욕 해를 초기해로 넣어 결과가 그보다 나빠지지 않는다.
  • S(기술 적합) = 요구 기술마다 min(보유 레벨 ÷ 요구 레벨, 1)을 중요도(1~5)로 가중 평균. 원천에 숙련 레벨이 없어 경력 개월을 대리 레벨로 바꾼다(경계 12·36·60·96개월). C(협업) = 0.4·min(함께한 개월 ÷ 12, 1) + 0.6·동료 평가 점수(평가 글 극성은 LLM 판정).
  • P = |C| 상위 200쌍만 보상한다 — 쌍 변수는 (쌍 수 × 사업 수)라 5,000쌍이면 200명에서 600초에도 빈자리 57석, 300명은 해가 없었다. F = 익숙한 쌍(최근 36개월 중 12개월 이상 같은 사업) 전부를 감점 — 오래 붙어 다닌 사이만 몰리는 팀을 흩는다. 단 지금 같은 진행 사업에 함께 있는 두 사람은 그 사업에 계속 있는 한 감점하지 않는다(팀 유지는 벌점 없음, 사용자 결정 10-19).
  • 필수 기술은 하드 제약이 아니라 S로 유도하고(실제 자료 답변 "선호"), 정원에 적히지 않은 등급은 예산·가용률 안에서 자유롭게 고를 수 있다.

6.2 대안과 운영 중 증분 최적화

  • 대안 B~D: 앞선 안과 (사람, 사업) 겹침 ≤ 80%인 다양성 컷 + 품질 하한(A − 5%). 빈 팀·중복·A보다 빈자리가 많은 후보는 버리고, 없으면 "조건을 만족하는 대안 없음"으로 억지로 채우지 않는다.
  • 운영 중 K: 기존 배치를 그대로 두고 사람마다 0/1 이동 변수를 두어 Σ ≤ K. 옮긴 사람은 "원래 없던 사업"에 들어가야 한다(빼서 놀리는 해 차단), 잠근 사람은 옮기지 않는다. 빈자리 감점(자리당 100)이 섞인 목적에서 5% 허용 차이는 1~2명 이동의 개선(1~2점)을 통째로 가리므로 허용 차이 0으로 풀어 최선을 증명한다.

6.3 솔버 운영

  • 시드 포트폴리오: 같은 모델을 시드만 바꾼 HiGHS 프로세스 4개로 동시에 풀어 가장 좋은 해를 고른다. 1시드면 조밀한 데이터에서 대안이 품질 하한에 걸려 안 A만 나오는 일이 있었다. 모델은 프로세스 시작 뒤 전용 파이프로 넘긴다 — 시작 인자로 넘기면 자식이 시작 중 죽을 때 부모가 멈췄다(실측).
  • 증명 상한을 함께 기록해 "최적값이 최대 몇 % 높을 수 있음"으로 보여 준다. 전일 투입 권장 한도 100명 30초·200명 60초·300명 90초, 12개월은 ×4(측정 기반, 관리자 설정).
  • 계산 멈추기: 사용자가 멈추면 풀던 안은 그때까지의 해로 끝나고(종료 사유 "사용자가 멈춤", 시간 한도와 구분) 다음 안은 시작하지 않는다. 연결이 끊기면 즉시 중단한다.
  • 편성 기록: 한 번의 편성(원천 CSV · 평가 글 판정값 · 계산 설정 · 편성안 · 운영 중 K 비교)을 JSON 파일 하나로 내보내고 다시 불러온다. 불러올 때 원천을 업로드와 같은 검증으로 다시 만들고 편성안을 지금 평가기로 다시 채점해 위반이 있으면 받지 않는다. 기록이 주장하는 솔버 증명은 이 서버가 확인할 수 없어 버린다 — 화면·PDF는 "재채점 통과 · 기록에서 불러옴"으로 표시하고, 증명은 다시 계산해야 붙는다.

6.4 독립 검증기와 평가기

  • 솔버가 낸 원시 해를 제품 MILP 코드와 별개로 다시 계산한다: 결측·NaN·범위·0/1, 월별 가용률·월 예산·등급 정원·동시 사업, 쌍 범위, 목적 4항, 그리고 화면에 내보낼 명단. 검증할 수 없는 값을 0으로 채우지 않는다.
  • HiGHS는 z = 1.0000000000000007 같은 값을 돌려준다 — 1e-9 안쪽의 경계 잔차만 경계로 옮기고(원본 보존), 예산의 극미세 초과(상대 1e-7 이하)는 투입률 보정 LP 뒤 다시 검증한다. 이 처리 없이는 HiGHS 해가 전부 "검증 실패"였다(실측).
  • 평가기는 어떤 배치든 현행 목적·제약 전체로 다시 채점한다 — 교체 검토(참고값), 보강, 단순 규칙 비교, 편성 기록 확인, PDF가 모두 같은 잣대를 쓴다.

6.5 검사받는 생성형 AI

쓰임AI가 하는 일기계 검사실패하면
평가 글 판정동료 평가 글의 극성(긍정/부정)을 판정 → 협업 점수 C에 반영. 판정값은 데이터 버전에 포함출력 형식·범위평가 항목 점수 사용
교체 설명(RAG)근거 색인에서 뽑은 동료 평가·점수 변화로 설명, 평가를 출처 번호와 함께 인용인용이 원문과 한 글자도 다르지 않은지, 출처가 실제로 있는지, 위반 교체면 첫 문장이 보류 결론인지, 인정 경력의 출처 표기규칙 기반 설명(출처 누락은 서버가 한 문장 덧붙임)
소명 글(GraphRAG)지식 그래프에서 만든 사실 목록 {F#} 중 무엇을 쓸지 고르고, 정해진 문법(주어·라벨·연결 말·맺음말)으로만 엮음. 숫자·충족 여부는 서버가 채움없는 자리표시, 허용 목록 밖 연결 말, 팀원 아닌 ID, 사실과 라벨의 짝, 사람별 사실 누락. AI가 빠뜨린 불리한 사실은 서버가 마지막 문단에 덧붙임정해진 틀의 글

소명 글은 처음에 자유 문장 + 금지어 목록으로 시작했으나 검토 때마다 뚫려, "AI는 사실 번호와 정해진 연결 말만 고르고 문장의 사실 부분은 서버가 채운다"로 바꿨다(E7b 94.7% → E7c 99.0%).

6.6 지식 그래프와 기술 이름 사전

  • 기술 이름 사전(개념 228개): "postgres"·"포스트그레스"·"PostgreSQL 14"처럼 갈린 이름과 버전 표기·괄호 병기를 한 이름으로 묶는다. 사전에 없는 이름은 합치지 않고 경고만 한다.
  • 하위 기술 부분 인정: 하위 기술 경력의 0.7깊이를 상위 기술에 인정(Spring → Java)하고, 인정으로 정해진 경력은 출처·개월을 따로 남겨 화면·설명·소명 글에서 본인 경력과 구분한다. 사전 버전과 인정 비율은 계산 버전에 들어가, 바꾸면 이전 캐시·미리 계산이 쓰이지 않는다.
  • 지식 그래프(core/kg): 사업·요구 기술·팀원·협업·후보 비교·규칙 준수를 사실로 만들어 소명 글에 쓰고, 기술마다 실무 가능·숙련·비어 있는 사람·요구 사업을 모아 조직 기술 지도를 만든다. 저장 기술은 측정으로 골랐다(8월 Neo4j 우위 0/20 → 제거, 10월 RDF 표준 추론은 가중 부분 인정을 표현하지 못해 인메모리 그래프 유지).

8.2 비용 구조(측정값)

  • 솔버 라이선스 0원 — 오픈소스 HiGHS로 300명 안 A를 최선 대비 0.9% 안에서 푼다(92초에 증명, 대안 B~D 3.3~3.5%). 상용 솔버(Gurobi)는 연간 견적제이고, 무료판은 변수 2,000개 제한이라 100명 모델도 넘는다.
  • AI 호출 비용은 무시할 수준 — 300명 조직의 평가 글 4,012건을 처음 판정하는 데 약 $0.32(이후 저장값 재사용), 사업 60건 소명 글 전체 약 $0.05, 교체 설명 한 건 약 $0.0006.
  • 서버 한 대 — 개발용 데스크톱 한 대에서 300명 계산·PDF까지 돌렸다. 사내 LLM으로 바꿀 때의 차이도 미리 쟀다(3.6).

8.4 차별점과 도입·확장 경로

  • 차별점: ① SI의 등급 정원·월 예산·휴직·협업 이력을 현업 규칙(전일 투입·사람 단위 동시 수행) 그대로 하나의 최적화로 풀고 증명 상한과 독립 검증으로 "얼마나 믿어도 되는지"까지 보인다. ② 가장 잦은 실무 결정인 "최소 인원 이동 재편성"을 최선 증명으로 푼다. ③ AI는 검사받는 부품이라 설명 글을 자동화하면서도 근거를 대조한다.
  • 실제 도입 시 단계(이 PoC의 범위 밖 — PoC는 가상 데이터로만 개발·검증했다): 섀도 운영(실제 편성과 나란히 3개월, 빈자리·예산 초과·재배치 횟수·고객 교체 요청·편성 소요 시간 기록) → 한 사업부 파일럿 → 전사·그룹사 확대. 그때 필요한 작업은 인사 시스템 연결 설정(받기 경로는 있고 가짜 인사 시스템으로만 시험), 사내 LLM 연결, 계정·권한·감사·배포 같은 운영 기능이다.
  • 결재 연결(실제 도입 시): 이 서비스는 검토 자료(PDF·링크)를 만들어 사내 전자결재에 올리고 결과를 받아 반영한다. 역할은 나눈다 — 부서장(편성 담당)은 계산·명단 수정·검토 요청, 팀장·인사팀(검토자)은 같은 화면을 읽기 전용으로 보고 의견·승인·반려(사유 필수)만 한다(검토자가 명단을 바꿀 수 없다). 흐름은 작성 중 → 검토 요청 → 팀장 승인 → 인사팀 승인 → 확정이고, 실제 배치는 마지막 승인 때만 바뀐다. 검토 요청 시점의 자료는 서버 서명으로 고정하고 그 사이 데이터가 바뀌면 승인을 무효로 해 다시 요청한다. 원래 사업 측 동의(팀장·부사장·인사팀 경유 등)는 자료의 "원래 사업이 잃는 것"·"합의" 칸이 근거가 된다. 계정은 사내 SSO. 이 PoC의 확정은 검토 요청 없이 바로 반영하는 단순화다.
  • 효과 입증 경로(실제 도입 시): 승인된 과거 성과(고객 평가·교체 요청·후속 수주)로 모델 가정을 점검하는 도구(core/evaluate/outcome_check.py)와 계산 버전 관리가 이미 있어, 실제 성과가 쌓이면 계수를 보정하고 효과를 숫자로 보일 수 있다.
  • 확장성: 입력 계약·평가기·검증기·지식 그래프는 업종에 묶이지 않아, 사람을 프로젝트 단위로 배치하는 조직(컨설팅·엔지니어링 등)에 같은 구조로 쓸 수 있다.

9. 한계와 다음 단계

  • 사업 효과는 실제 성과 자료로 확인하기 전이다(NOT_CALIBRATED). 모든 수치는 가상 데이터와 설계한 점수표 안에서 잰 값이다 — 실제 도입 시 섀도 운영(8.4)으로 확인한다.
  • 점수의 계수(협업 0.3·익숙한 사이 0.2·하위 기술 70%·경력 레벨 경계)는 설계값이다. 실제 성과로 보정할 수 있게 계산 버전과 평가기를 분리해 두었다.
  • 평가 글은 생성기가 쓴 가상 글이다. 실제 글로 판정 정확도를 다시 잰다(E4 측정 도구 그대로).
  • 운영 기능은 시제품 수준이다(관리자 계정 하나·단일 서버). 전일 투입은 가용률 0 또는 1을 전제로 한다(시간제는 실제 도입 시 다시 정한다).
