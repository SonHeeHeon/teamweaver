1. 과제 개요

1.1 배경과 문제

SI 조직에서는 한 사람이 여러 사업에 걸쳐 일한다. 배치를 정하려면 기술 적합만이 아니라 사람마다 달마다 남은 시간(가용률), 사업의 등급별 정원과 월 예산, 함께 일해 본 동료(협업 이력)를 동시에 맞춰야 한다. 한 조건을 맞추면 다른 조건이 깨지기 쉬워, 담당자의 수작업 배치로는 ① 조건 위반 여부, ② 더 나은 배치가 있었는지, ③ 인사팀에 "왜 이 팀인가"를 설명할 근거를 확인하기 어렵다. 상황은 셋이다 — 가장 잦은 신규 사업 편성(대부분 이미 일하는 중, 쉬는·끝나 가는 사람과 몇 명만 옮겨 새 사업 팀을 짬), 진행 사업에 이슈가 생긴 긴급 투입, 드문 연간 계획(백지에서 6개월 배치).

1.3 범위와 전제

  • PoC·과제 제출용이다. 실제 인사 자료는 적재하지 않았다(적재 불가). 입력 형식은 실제 인사 자료의 항목과 규칙을 받아 설계했고, 개발·검증·시연은 같은 형식의 가상 데이터로 했다.
  • 점수의 계수(협업 0.3·익숙한 사이 감점 0.2·하위 기술 인정 70% 등)는 설계값이다. 결과를 맞추려고 데이터 생성기나 계수를 조정하지 않았고, 실패·중단도 기록에 남겼다.

1.5 현업 수행 경험에서 나온 요구

업무 규칙과 가상 데이터의 모양은 대부분 과제 수행자가 SI 사업을 직접 수행하며 겪은 현업 경험에서 나왔고, 결과를 직접 보며 여러 번 바로잡았다.

현업에서 본 실제(요구)반영한 것
그룹 단위 조직, 배치 대상은 내부 정원뿐. 오래전 경력은 잘 기억되지 않는다조직형 묶음 100·200·300명, 최근 10년 이력만

부서장이 정하면 팀장·인사팀이 확인한다. 숫자만으로는 소명이 안 되고, 빼 온 사업의 영향도 설명해야 한다인사팀 검토 자료(잠긴 사실 + 부서장 판단·해명·이의), 기간별 변경 보고서(모든 변경을 지우지 않는 기록 → 한 PDF), 결재는 사내 전자결재로(8.4)
대부분 100% 가용, 약 3%는 해를 걸친 1년 육아휴직, 약 2%는 한 달 휴가(사업이 자체 감당). 계획은 1년 단위로도 짠다가용률 가정(v3), 쉬는 달이 걸린 사람은 사유와 함께 비활성, 계획 기간 6·12개월
사업도 나이가 섞여 있다 — 2024년 시작한 운영 사업(내부 소수), 2025년 사업의 고도화, 2026년 상반기 시작, 운영 사업에 6달 붙는 추가 과제(회사 2명, 외주 여럿). 연초 계획도 대부분 진행 중인 사업이다사업 수명 주기 섞기(v4·v5): 원래 시작 달·단계 표시, 추가 과제의 상위 사업·외주 참고값(계산에 안 씀), 진행 사업 경력을 이력·평가에 이음
부서장은 모범 안보다 지금 실제 배치에서 "이 사람을 바꾸면?"을 본다. 고른 안은 확정해야 배치가 되고, 잘못 확정한 한 건은 그것만 되돌린다연간 계획(① 조건 → ② 비교·확정)과 What-if(지금 배치) 분리, 안 확정 + "지금 대비 옮김", 변경을 담아 한 번에 확정, 확정 취소
중급 자리에 초급을, 중급이 없으면 고급을 넣기도 한다 — 막을 일이 아니라 사유를 남길 일이고, 예산을 넘으면 증액을 함께 올린다등급 대체(위·아래, 사유 필수, 넘친 예산 증액) — 검토 자료의 사실로 남음

4. 정성적 성과

  • 계산 결과를 얼마나 믿어도 되는지 함께 보여 준다. 모든 결과에 "규칙 위반 없음 확인", "최선 증명" 또는 "최적값이 이 해보다 최대 몇 % 높을 수 있음", "시간 한도 도달·사용자가 멈춤·기록에서 연 결과"를 붙이고, 교체 점수는 "참고값 · 재최적화 아님"으로 밝힌다. PDF의 이 문구도 서버 서명이 맞을 때만 찍힌다.
  • 생성형 AI를 "검사받는 부품"으로 썼다. 결정은 최적화가, 읽기와 쓰기는 AI가 맡는다는 경계를 실험으로 정했다 — LLM 직접 배치(3.4)는 규모가 커지면 무너지고, 평가 글 판정(3.5)은 규칙으로는 안 된다. AI 글은 기계 검사를 통과해야 나가고(소명 글은 사실 번호와 연결 말만 고르고, 교체 설명은 인용을 원문과 대조), 걸리면 규칙 기반 글로 대신한다.
  • 규칙을 측정으로 정했다. 보상 쌍 수·익숙한 쌍 기준·감점 방식·솔버·소명 글 방식을 대안과 같은 데이터로 비교하고, 판정 기준을 측정 전에 커밋했다(7장).
  • 부서장의 판단을 지우지 않고 남긴다. 계산이 정하지 않는 것 — 등급 대체, 프로젝트 동시 수행 허용, 확정 취소 — 은 부서장이 사유와 함께 고르고, 데이터의 새 판(되돌리기 가능)과 인사팀 검토 자료의 잠긴 사실로 남는다. 계산 모델은 그대로 두어 부족 신호를 묻지 않는다.
  • 측정한 대로 보고한다. 사업 효과는 NOT_CALIBRATED로 표시하고, 가상 성과로 효과를 "입증"하는 것은 순환 검증이라 하지 않았다. 대안 C가 A보다 조금 높은 것처럼 직관에 어긋나는 결과도 그대로 둔다.
  • 실제 도입을 염두에 둔 설계. 실제 인사 자료와 같은 입력 계약·검증 리포트, 평가 원문을 화면·AI에 보내지 않고 항목 라벨만 쓰는 비공개 모드, 외부 AI 차단 규칙, 사내 LLM 전환 시 차이 측정(3.6).
  • AI로 개발 과정 자체를 운영했다. Claude 두 계정과 Codex가 파일 소유 영역을 나눠 병행 개발하고(작업 분담표·인수인계 기록), 변경은 커밋 전에 독립 리뷰를 받았다. 리뷰 지적은 실패하는 시험으로 먼저 고정하고, 측정은 판정 기준을 먼저 커밋했다 — 12주 동안 커밋 약 610개, 시험 2,140개.

6.1 배치 최적화 모델 (혼합정수계획, MILP)

목적(최대화)Σi,j Sij·zij + λ·Σ(p,q)∈P, j Cpq·ypqj − μ·Σ(p,q)∈F, j ypqj − 100·Σj,g slackjg   (λ = 0.3, μ = 0.2)
전일 투입 자격zij = 0  (사업 j 기간 중 가용률im < 1인 달이 있으면 — 육아휴직 등)
프로젝트 동시 수행Σj: m∈j zij ≤ 동시 수행 상한i  (달 m마다. 기본 1, 부서장이 사유와 함께 허용한 사람만 2)
월 예산Σi 단가i·zij ≤ 예산j  (동시 수행자는 사업마다 전액)
등급 정원Σi∈g zij + slackjg = 요구 인원jg  (사업에 적힌 등급 g만)
쌍 선형화ypqj ≤ zpj,  ypqj ≤ zqj,  ypqj ≥ zpj + zqj − 1
  • 변수: z 배치 여부(0/1 — 전일 투입이라 투입률 변수가 없다, 예전 투입률 방식은 설정에 남김), y 두 사람이 같은 사업에 있는지(곱의 선형화), slack 등급 정원 미충원(큰 감점, 결과에 노출). 탐욕 해를 초기해로 넣는다.
  • S(기술 적합) = 요구 기술마다 min(보유 레벨 ÷ 요구 레벨, 1)을 중요도(1~5)로 가중 평균. 원천에 숙련 레벨이 없어 경력 개월을 대리 레벨로 바꾼다(경계 12·36·60·96개월). C(협업) = 0.4·min(함께한 개월 ÷ 12, 1) + 0.6·동료 평가 점수(평가 글 극성은 LLM 판정).
  • P = |C| 상위 200쌍만 보상한다(5,000쌍이면 200명에서 600초에도 빈자리 57석). F = 익숙한 쌍(최근 36개월 중 12개월 이상 같은 사업)을 감점해 오래 붙어 다닌 사이만 몰리는 팀을 흩는다 — 지금 같은 진행 사업에 함께 있는 두 사람은 그 사업에서 감점하지 않는다(사용자 결정 10-19).
  • 필수 기술은 하드 제약이 아니라 S로 유도하고(실제 자료 답변 "선호"), 정원에 적히지 않은 등급은 예산·가용률 안에서 자유롭게 고를 수 있다.

6.2 대안과 운영 중 증분 최적화

  • 대안 B~D: 앞선 안과 (사람, 사업) 겹침 ≤ 80%인 다양성 컷 + 품질 하한(A − 5%). 빈 팀·중복·A보다 빈자리가 많은 후보는 버리고, 없으면 "조건을 만족하는 대안 없음"으로 억지로 채우지 않는다.
  • 운영 중 K: 기존 배치를 그대로 두고 사람마다 0/1 이동 변수를 두어 Σ ≤ K. 옮긴 사람은 "원래 없던 사업"에 들어가야 한다(빼서 놀리는 해 차단), 잠근 사람은 옮기지 않는다. 빈자리 감점(자리당 100)이 섞인 목적에서 5% 허용 차이는 1~2명 이동의 개선(1~2점)을 통째로 가리므로 허용 차이 0으로 풀어 최선을 증명한다.
  • 확정과 등급 대체: 모든 확정은 원천 CSV 묶음을 고쳐 업로드와 같은 검증으로 켜는 새 판이고, 새로 생기거나 커진 위반·고정 배치 빼기를 거절한다. 손 편성이 새로 넘친 등급 × 모자란 자리를 만들면 가까운 등급부터 짝지어 정원을 바꾸고(사유 필수, 넘친 예산 증액), 미리 계산·What-if 채점·확정 검증이 같은 함수를 쓴다. 다른 사업에서 빼 와 생긴 빈자리는 같은 확정에서 메우거나 "메우지 않음"(사유, 그 정원을 줄임)을 정해야 확정된다. 연간 계획은 고정이 있으면 계산 전에 유지·풀기를 묻는다.

6.3 솔버 운영

  • 시드 포트폴리오: 같은 모델을 시드만 바꾼 HiGHS 프로세스 4개로 동시에 풀어 가장 좋은 해를 고른다(1시드면 조밀한 데이터에서 대안이 품질 하한에 걸려 안 A만 나오기도 했다). 모델은 시작 뒤 전용 파이프로 넘긴다 — 시작 인자로 넘기면 자식이 시작 중 죽을 때 부모가 멈췄다(실측).
  • 증명 상한을 함께 기록해 "최적값이 최대 몇 % 높을 수 있음"으로 보여 준다. 전일 투입 권장 한도 100명 30초·200명 60초·300명 90초, 12개월은 ×4(측정 기반, 관리자 설정).
  • 계산 멈추기: 사용자가 멈추면 풀던 안은 그때까지의 해로 끝나고(종료 사유 "사용자가 멈춤", 시간 한도와 구분) 다음 안은 시작하지 않는다. 연결이 끊기면 즉시 중단한다.
  • 편성 기록: 한 번의 편성(원천 CSV · 평가 글 판정값 · 계산 설정 · 편성안 · 운영 중 K 비교)을 JSON 하나로 내보내고 다시 불러온다. 불러올 때 업로드와 같은 검증으로 다시 만들고 지금 평가기로 다시 채점해 위반이 있으면 받지 않는다. 기록이 주장하는 솔버 증명은 버린다 — 화면·PDF는 "위반 없음 · 기록에서 연 결과", 증명은 다시 계산해야 붙는다.

6.4 독립 검증기와 평가기

  • 솔버가 낸 원시 해를 제품 MILP 코드와 별개로 다시 계산한다: 결측·NaN·범위·0/1, 월별 가용률·월 예산·등급 정원·동시 사업, 쌍 범위, 목적 4항, 그리고 화면에 내보낼 명단. 검증할 수 없는 값을 0으로 채우지 않는다.
  • HiGHS는 z = 1.0000000000000007 같은 값을 돌려준다 — 1e-9 안쪽의 경계 잔차만 경계로 옮기고(원본 보존), 예산의 극미세 초과(상대 1e-7 이하)는 보정 LP 뒤 다시 검증한다. 이 처리 없이는 HiGHS 해가 전부 "검증 실패"였다(실측).
  • 평가기는 어떤 배치든 현행 목적·제약 전체로 다시 채점한다 — 교체 검토·What-if(참고값), 확정 미리 계산, 단순 규칙 비교, 편성 기록 확인, PDF가 모두 같은 잣대를 쓴다.

6.6 지식 그래프와 기술 이름 사전

8.4 차별점과 도입·확장 경로

  • 차별점: ① SI의 등급 정원·월 예산·휴직·협업 이력을 현업 규칙(전일 투입·사람 단위 동시 수행·등급 대체) 그대로 하나의 최적화와 확정 규칙으로 풀고, 증명 상한과 독립 검증으로 "얼마나 믿어도 되는지"까지 보인다. ② 가장 잦은 "최소 인원 이동 재편성"을 최선 증명으로 푼다. ③ AI는 검사받는 부품이라 설명 글을 자동화하면서도 근거를 대조한다.
  • 실제 도입 시 단계(PoC 범위 밖): 섀도 운영(실제 편성과 나란히 3개월, 빈자리·예산 초과·재배치·고객 교체 요청·편성 시간 기록) → 한 사업부 파일럿 → 확대. 그때 할 일은 인사 시스템 연결 설정(받기 경로는 있고 가짜 인사 시스템으로만 시험), 사내 LLM 연결, 계정·권한·감사·배포다.
  • 결재 연결(실제 도입 시): 검토 자료를 사내 전자결재에 올리고, 팀장·인사팀은 같은 화면을 읽기 전용으로 보며 승인·반려만 한다. 배치는 마지막 승인 때 바뀐다(이 PoC의 확정은 바로 반영하는 단순화).
  • 효과 입증 경로(실제 도입 시): 과거 성과 점검 도구(core/evaluate/outcome_check.py)와 계산 버전 관리로, 성과가 쌓이면 계수를 보정한다.
  • 확장성: 입력 계약·평가기·검증기·지식 그래프는 업종에 묶이지 않아, 사람을 프로젝트 단위로 배치하는 조직(컨설팅·엔지니어링 등)에 같은 구조로 쓸 수 있다.
