## 1. 이번에 결정할 것과 결정하지 않을 것

**동일한 인력 배치 방정식을 CBC·HiGHS·SCIP 중 무엇이 더 안정적으로 푸는가?** 이를 작은 문제의 정답 검증 → 규모 확대 → 반복 측정 순서로 비교한다. 솔버는 방정식을 푸는 도구이지, 인력의 미래 성과를 학습한 AI 모델이 아니다.

| 판단 | 이번 실험의 증거 범위 |
|---|---|
| 방정식을 정확히 구현했는가 | 소형 정답기와 독립 제약 검증으로 확인 |
| 4분 내 쓸 수 있는 해를 반환하는가 | 명시된 합성 입력·호스트에서 측정 |
| 찾은 해가 수학적 최적값에 가까운가 | 검증된 해와 솔버의 최적값 상한으로 확인; 상한이 없으면 미확인 |
| 실제로 고객 만족·프로젝트 성과가 좋아지는가 | **확인 불가 / NOT_CALIBRATED** |
| 아직 모르는 실제 컬럼·분포에서도 같은 솔버가 최고인가 | **확인 불가**. 컬럼 정의가 오면 별도 버전으로 재실험 |

기존 Phase 0 설계의 “컬럼 공유 후 24시간 비교” 보류를 사용자의 이번 요청에 따라 **가상 입력에 한정해 해제**한다. 실제 데이터 적합성과 사업 성과 검증 보류는 그대로다. 예전 `outputs/plan6-solver-benchmark-design.html`의 실행 횟수·95% 점수비·후속 Phase 2 시간 배정은 본 설계로 대체한다. 과거 문서는 이력으로 보존한다.

이번에는 서비스 API/UI 변경, 가중치 학습, 상용 솔버, 유료 API 호출, 클라우드 생성, 실제 인사정보 수집을 하지 않는다. warm start·pair cap 튜닝·다중 스레드 비교도 별도 Phase로 남긴다. 24시간을 억지로 채우지 않는다.

## 2. 기술 후보와 선정 근거

| 후보 | 포함/보류 이유 | 연결 방안 및 확인 사항 |
|---|---|---|
| CBC | 현재 구현 기준선; 변경 전후 비교의 기준 | 기존 PuLP CBC 경로. 실제 실행 바이너리·버전·옵션·로그 보존 |
| HiGHS | 같은 혼합정수 선형모델을 푸는 독립 후보 | PuLP HiGHS + highspy. 설치 호환성과 native 상태·bound 취득 확인 |
| SCIP | 다른 탐색·전처리 전략의 혼합정수 후보 | PuLP SCIP_PY + PySCIPOpt. Python 3.12/macOS arm64 지원을 실제 설치로 확인 |
| OR-Tools CP-SAT | 이번 정면 비교에서 보류 | 정수 기반이므로 현재 연속 투입률 `a`를 이산화하면 문제 자체가 달라짐. 추후 모델 변경 실험으로 분리 |
| 상용 솔버 1종 | 사용자 최신 선택에 따라 보류 | 오픈소스 결과 이후 필요성과 견적을 별도로 비교 |

모델링 도구는 PuLP를 유지한다. Pyomo나 직접 native 모델 구축으로 동시에 바꾸면 “솔버 차이”와 “모델 재작성 차이”가 섞인다. 기존 모델 생성부를 공통 builder로 분리하고, 어댑터만 교체하는 방식을 채택한다. MPS 파일 입출력 통일안도 고려했지만 매핑·직렬화 비용과 정밀도 문제가 있어 1차 경로로 쓰지 않는다. 공통 모델의 정규화 계수 해시와 진단용 내보내기를 남긴다.

기본 접근은 **고정 모델·고정 옵션 비교**다. 솔버별 세밀한 튜닝을 먼저 하는 접근은 조정 시간과 데이터 과적합이 섞이므로 제외한다. 특정 솔버가 항상 빠르다고 미리 가정하지 않는다.

### 라이선스와 비용

공식 자료 확인일: 2026-09-21. CBC는 EPL-2.0, SCIP는 Apache-2.0, HiGHS core는 MIT다. HiGHS의 선택적 HiPO/배포 패키지에는 다른 라이선스 조건이 있으므로 실제 설치물과 전이 의존성의 고지 파일을 보존한다. 이것을 배포 법률 검토 완료로 취급하지 않는다.

- 본 설계의 오픈소스 솔버 사용료: **추가 라이선스 구매 0원**. 상용 견적은 이번에 산정하지 않는다.
- 템플릿 생성 + 규칙 기반 리뷰 파싱만 사용: 실험의 LLM/API 호출료 **0원**.
- 기존 로컬 컴퓨터에서 실행: 추가 클라우드 청구 **0원**. 전기·기기 점유·개발 인건비는 0원이 아니다.
- 전력량은 측정 전 미정. 예를 들어 평균 추가 소비전력 50W라면 24시간에 1.2kWh; 비용은 `측정 kWh × 실제 적용 단가`다. 50W는 실측치가 아니다.
- 미래 호스팅 비용은 `인스턴스 시간당 단가 × 점유 시간 + 저장/전송`으로 별도 계산한다. 이번 macOS 결과로 클라우드 비용이나 동시 처리량을 단정하지 않는다.

근거: [CBC 공식 저장소](https://github.com/coin-or/Cbc), [HiGHS 공식 저장소](https://github.com/ERGO-Code/HiGHS), [SCIP 공식 저장소](https://github.com/scipopt/scip), [PySCIPOpt 설치 문서](https://pyscipopt.readthedocs.io/en/latest/install.html), [PuLP 솔버 연결 문서](https://coin-or.github.io/pulp/guides/how_to_configure_solvers.html), [CP-SAT 정수 모델 요구](https://developers.google.com/optimization/cp/cp_solver).

## 3. 무엇을 동일하게 고정하는가

모델은 현재 `core/optimize/milp.py`의 Plan A MILP다. `z`는 사람의 프로젝트 선택, `a`는 연속 투입률, `y`는 함께 배치된 인력 쌍, `slack`은 미충원이다. 목적함수는 스킬 + 시너지 − 과도한 반복 협업 − 미충원 페널티다.

- `lam=0.3`, `mu=0.2`, `min_alloc=0.2`, `clique_threshold_months=6`, `slack_penalty=100` 고정. 현실에 맞게 보정된 값이라는 뜻은 아니다.
- `pair_keep_ratio=0.15`, `max_pairs=5000` 고정. 보상 pair와 반복 협업 penalty pair는 별도 계산하며 동일 집합을 세 솔버에 공급한다.
- 전체 모델은 **이 pair 절삭 정책이 적용된 모델**이다. 5% gap은 이 모델 기준이며, 절삭 전 전체 문제의 5% 보장을 뜻하지 않는다.
- 입력 JSON, S/C 행렬, 사람/프로젝트 순서, pair 집합, 제약/목적 계수·변수 경계를 정규화해 SHA-256으로 남긴다. 같은 입력 블록 내 하나라도 다르면 비교하지 않는다.
- 실제 옵션과 버전을 고정한다. 기존 환경의 PuLP 3.x를 기준으로 검증하며 온라인 최신 문서 때문에 자동으로 메이저 업그레이드하지 않는다.
- 각 솔버 **1 thread**, 동시 실행 1개, cold process, warm start 없음. BLAS/OpenMP 보조 스레드도 1로 제한하고 적용 여부 기록.
- native relative/absolute MIP gap 목표는 0으로 설정한다(허용오차까지의 증명 탐색). 솔버별 서로 다른 “5%” 분모를 조기 종료 기준으로 섞지 않는다. 결과 판정의 공통 gap은 §6에서 계산한다.
- 동일한 문제에서 결과가 같아야 하는 것은 제약과 목적값이지, 선택된 사람 목록 자체가 아니다. 동점 최적해가 여러 개일 수 있다.

현재 기록된 호스트는 macOS arm64, 10 CPU, 16GB 메모리다. 실제 실행 시작 때 다시 수집한다. **1 thread 제한은 1 vCPU 하드웨어 격리가 아니며**, 이 실행을 “4 vCPU 서비스 환경 검증”이라고 쓰지 않는다. CPU 모델·OS·전원 상태·백그라운드 부하를 기록하고 무거운 다른 작업과 동시 실행하지 않는다.

## 4. 합성 입력: 4규모 × 4조건 × 3개 seed

규모: **50명/10프로젝트 → 100/20 → 200/40 → 300/60**. 기간은 기존 생성기의 6개월을 유지한다.

공통 생성기 `core/datagen/generator.py`는 변경하지 않고 별도 scenario 변환층을 둔다. `experiments/bench/datasets.py`의 캐시 객체를 직접 수정하지 않는다. 생성 후 deep copy 또는 불변 스냅샷을 사용한다. 결과를 좋게 만들려고 기술 난도·프로젝트 요구를 사후 수정하지 않는다.

| 조건 | 사전 고정 변환 | 반드시 남길 관측량 |
|---|---|---|
| 기본 | 기존 생성 그대로 | 월별 수요/공급, 등급별 수요, 가용성·예산 분포 |
| 가용성 압박 | 아래의 수요/공급 비율을 기준으로 가용성만 축소 | 목표와 실제 비율, 등급·기간별 병목, 미충원 |
| 예산 압박 | 기본 입력의 프로젝트 월 예산 × 0.85 | 변환 전후 예산, 예산 사용량, 미충원 |
| 협업 관계 밀집 | 중복 없는 무방향 협업 간선을 총 `round(5.5 × 인원수)`개까지 결정적으로 추가 | 실제 평균 차수, 협업 월수, C 비영 비율, penalty/reward pair 수와 y 변수 수 |

가용성 압박의 정의: 각 월의 활성 프로젝트 요구 인원 합을 D_m, 가용률 합을 A_m으로 두고 `r=max(D_m/A_m)`(양의 공급 월 기준)이다. `q=min(1,r)`를 모든 사람의 가용률에 곱해 peak 비율을 1.0으로 만든다. r=0 또는 수요가 있으나 공급이 0인 입력은 변환 불가로 명시한다. 이 비율은 **명목 인원 압박 지표**이며 연속 투입률·등급·예산 때문에 실제 가능/불가능을 판정하지 못한다. 기본 생성기의 capacity calibration은 기본 생성 시 한 번만 적용하고 변환 후 다시 적용하지 않는다.

밀집 조건은 기존 간선을 보존하고 정렬된 미사용 pair 중 scenario seed로 추가 대상을 뽑는다. 추가 간선의 월수는 기존 생성기와 같은 1~18 범위, 템플릿 리뷰/규칙 파서도 같은 규칙을 쓴다. 리뷰 수는 사람당 기존 2~4 범위를 유지하되 협업 상대에서 선택한다. 관계 밀집이 모든 pair의 긍정적 시너지 증가를 의미하지 않으며 C의 실제 분포를 공개한다. 입력 확정 후에는 솔버 결과를 보고 관계나 리뷰를 바꾸지 않는다.

- 설치/파일럿 seed: 42. 평가용 seed: **100, 101, 102**. 파일럿은 본평가 요약에서 제외한다.
- 48개 평가 입력을 실행 전 동결한다. 입력 생성 seed와 솔버 내부 탐색 seed를 별도로 기록한다.
- 반복 실행은 같은 입력과 같은 솔버 seed/옵션으로 시스템 변동을 측정한다. 서로 다른 seed의 난이도 다양성을 반복 횟수로 과장하지 않는다.
- 규칙 파서 기반 합성 리뷰는 실제 자유서술 분포를 대표하지 않는다. 기존 LLM demo fixture와도 별도 데이터셋으로 표시한다.

## 5. 최대 24시간 실행표

1회는 “입력 하나를 솔버 하나로 풀고 독립 검증·결과 저장까지 마치는 슬롯”이다. 예산은 시작 전에 계산하며 부족하면 해당 슬롯을 시작하지 않는다.

| 순서 | 구성 | 최대 횟수 | 슬롯 제한 | 최대 슬롯 합 |
|---|---|---:|---:|---:|
| 1. 정답 대조 | 기존 7개 소형 정답 케이스 × 3솔버 | 21 | 30초 | 10분 30초 |
| 2. 설치 확인 | 50/10 기본 seed42 × 3솔버 | 3 | 60초 | 3분 |
| 3. 파일럿 | 100/20·200/40·300/60 기본 seed42 × 3솔버 | 9 | 120초 | 18분 |
| 4. 본평가 | 4규모 × 4조건 × 3seed × 3솔버 × 2반복 | 288 | 240초 | 19시간 12분 |
| 5. 300명 재확인 | 300/60 × 4조건 × 3seed × 3솔버 × 1추가 반복 | 36 | 240초 | 2시간 24분 |
| 합계 | 준비 점검 33 + 평가 324 | **357** | — | **22시간 7분 30초** |
| 여유 | 입력 준비·프로세스 정리·저장·복구·최종 요약 | — | — | **1시간 52분 30초** |

총 상한은 **86,400초**다. 슬롯 한도 합은 79,650초, 여유는 6,750초. 이는 최대 예약량이지 실제 소요시간 예측이 아니다. 일찍 끝난 슬롯의 남은 시간은 반환하지만 새 실험을 임의로 추가하지 않는다. 설치/개발은 sweep 시작 전 작업이며, sweep을 시작한 이후의 준비·재시도·집계는 모두 총 예산에 포함한다.

본평가는 규모 순서로 진행하되 각 규모 안에서 입력 블록을 고정 seed로 섞는다. 동일 입력/반복의 세 솔버를 연속 실행하고 순서를 CBC→HiGHS→SCIP, HiGHS→SCIP→CBC, SCIP→CBC→HiGHS로 순환시킨다. 특정 솔버만 장시간 한꺼번에 실행해 발열이나 시간대가 편향되지 않도록 한다. 일정 전체는 실행 전에 manifest로 동결한다.

정답 검증 실패 솔버는 큰 실험으로 보내지 않는다. 설치 불가 솔버는 `UNAVAILABLE`, 미실행 슬롯은 `SKIPPED_DEPENDENCY`로 표시한다. 나머지 비교는 가능하지만 “3종 비교 완료”로 보고하지 않는다. 파일럿의 느림은 자동 탈락 사유가 아니다. 잘못된 해나 입력 오염은 탈락/일시 중지 사유다.

### 4분의 정확한 의미

슬롯 시계는 부모 프로세스가 자식을 시작하기 직전부터 동작한다. **동결된 도메인 입력 읽기 → graph/S/C 계산 → 모델 생성 → 어댑터 변환 → 최적화 → 원시 해 추출 → 독립 검증 → 결과 원자 저장**이 240초 안에 포함된다. 합성 원자료 생성·초기 동결 시간은 별도 준비 시간으로 총 24시간에만 포함한다. 미래 CSV/API 수집, 네트워크, UI 렌더링 지연은 이 측정에 포함되지 않는다.

솔버 제한은 `남은 슬롯 시간 − 10초`로 설정해 검증·저장 여유를 둔다. 시간이 부족하면 solve를 시작하지 않는다. 240초가 지나면 부모 감독자가 자신이 생성한 프로세스 그룹만 종료한다. 정리 지연도 별도 기록하고 24시간에 차감한다. OS 수준에서 정확히 240.000초 종료를 보장한다고 주장하지 않으며, 초과 완료는 `DEADLINE_EXCEEDED`다.

프로세스 트리 RSS를 0.5초 간격으로 관측하고 **12GiB 초과 감지 시** 중단한다. macOS에서 이 샘플링은 엄격한 메모리 하드캡이 아니며 순간 초과를 놓칠 수 있다. 메모리 압박/디스크 부족 시 다음 슬롯을 시작하지 않는다. 하드 격리가 필요한 서비스 검증은 추후 Linux 컨테이너 자원 제한으로 별도 수행한다.

## 6. 검증과 지표: 속도보다 먼저 정확성

### 선행 보강

현재 Phase 0 진단 경로는 누락 값을 `or 0.0`으로 치환하고 PuLP 상태를 중심으로 해석한다. 그대로 다중 솔버의 성공 판정에 쓰지 않는다. 먼저 아래 계약을 구현·테스트한다.

1. native 종료 이유, 해 존재 여부/개수, incumbent 목적값, best bound, 옵션, 원본 상태 코드를 보존한다. PuLP의 `Optimal` 문자열 하나로 전역 최적을 인정하지 않는다.
2. a/z/y/slack의 기대 key 집합과 실제 key 집합이 정확히 일치해야 한다. None, NaN, Infinity, 누락, 알 수 없는 key는 거절하고 0으로 보정하지 않는다.
3. z의 이진성 및 [0,1], a/y의 [0,1], slack의 비음수, 모든 도메인 제약을 솔버 객체를 읽지 않는 검증기로 다시 검사한다. 완화해를 정수 incumbent로 오인하지 않는다.
4. 원시 목적값을 네 항으로 재계산하고 표시용 배치안의 자원·예산·연결 제약도 재검사한다. 원시값과 표시값의 차이를 숨기지 않는다.
5. 작은 정답 케이스는 기존 절대오차 1e-6 기준을 유지한다. 큰 문제의 도메인 허용오차는 1e-6, 예산 합·목적값 비교는 `1e-6 + 1e-8 × max(1, |기준값|)`로 명시한다. 실제 residual 최대값을 함께 기록한다. 결과를 보고 허용오차를 늘리지 않는다.

Phase 0 정답기는 이진 조합 열거 + SciPy linprog다. HiGHS 후보와 연속 LP 엔진 계보를 공유할 수 있어 완전히 다른 엔진의 증명이라고 표현하지 않는다. 손계산 케이스와 CBC/SCIP의 교차 확인을 함께 쓰며, 큰 문제는 완전탐색 정답이 없는 것을 명시한다.

### 공통 품질 정의

모든 목적값은 **최대화 방향**으로 변환한다. 검증된 incumbent 목적값을 L, 같은 모델에 대한 솔버 상한을 U로 둔다.

`normalized_gap = max(0, U − L) / max(1, |U|, |L|)`

- L/U가 유한하고, U가 허용오차 이내에서 L 이상이어야 한다. 잘못된 방향·상한·파싱은 `BOUND_INVALID`다.
- U 미제공은 `BOUND_UNKNOWN`이며 검증된 배치안으로는 집계할 수 있지만 5% 품질 확인에는 통과하지 않는다.
- `quality_pass`: 독립 검증 통과 + 슬롯 내 저장 완료 + normalized_gap ≤ 0.05.
- `proven_optimal`: native 최적 증명 종료 + 유효한 bound/해 + 허용오차 내 U=L. 시간 제한 해를 전역 최적이라고 쓰지 않는다.
- 예: L=-100, U=-90이면 gap=10%. 음수 목적값에도 의미가 있는 정의다. 이는 **성과 90%**라는 뜻이 아니다.
- 후보 간 보조 비교: 같은 입력의 검증된 최고값 B에 대한 `(B−L)/max(1,|B|,|L|)`. 이름은 `best_observed_regret`이며 B를 진짜 최적값으로 부르지 않는다.
- 목적값의 상수 이동에 따라 정규화 gap이 바뀔 수 있으므로 목적함수 정의를 고정하고 절대차 U−L도 함께 공개한다.

CBC 로그의 내부 최소화 표기 등을 외부 최대화 방향으로 변환할 때 버전별 정상/시간제한/무해/음수목적 로그 fixture 테스트를 둔다. 추출할 수 없는 bound를 추정해 채우지 않는다. HiGHS/SCIP는 가능하면 native 수치 API를 사용한다.

### 필수 보고서

입력·규모·조건별로 다음을 기록한다.

- 설치/정답 검증 결과, 독립 검증 통과율, 제약 위반 종류·최대 residual.
- 검증된 해 반환율, 4분 내 `quality_pass` 비율, 증명된 최적해 비율.
- end-to-end/graph·scoring/build/adapter/solve/extract/validate/persist 시간. 파일럿에서 계측 중복이 없는지 확인.
- 유효 L/U, 절대 gap/정규화 gap, best-observed regret, 목적함수 네 항, 미충원, 예산/가용성 사용량.
- 변수·제약·pair 개수, 입력/모델 hash, peak RSS, 로그 크기, 실패/중단 원인.
- 시간 p50/p95/max와 개별 점을 모두 표시. 타임아웃을 성공 실행 평균에서 조용히 제외하지 않는다. 타임아웃은 우측 중도절단 값으로 표시하고 성공 실행 시간 통계와 별도 표기한다.

300/60은 솔버당 12개 독립 입력 × 3회 = 36회다. 반복 3회가 독립 데이터 36개를 뜻하지 않는다. 비교는 동일 입력끼리 짝지으며, 표본이 작으므로 p95는 탐색적 수치이지 서비스 SLA 보증이 아니다. 서로 다른 입력의 원점수를 평균 내 솔버 순위를 만들지 않는다.

### 선택 규칙

정확성 실패를 먼저 제외한다. 300/60에서 조건별 품질 통과율 → 유효 해 반환율 → 짝지은 gap 분포 → 시간·메모리·연동 복잡도를 순서대로 검토한다. 두 후보 간 차이가 작거나 조건별 승자가 바뀌면 **결론 유보 또는 조건부 후보**로 남긴다. 무조건 한 종을 승자로 만들지 않는다. 결과는 “현재 합성 모델의 잠정 기본 솔버” 추천일 뿐 생산 도입 확정이 아니다.

## 7. 체크포인트와 중단·재개

예정 산출물 경로(아직 runner 미구현):

```text
experiments/results/phase1/<run_id>/
  manifest.json           # 코드/환경/옵션/전체 일정/입력 해시
  inputs/                # 동결 합성 입력, pair·행렬 해시
  events.jsonl           # 순차 사건 기록; 마지막 불완전 행 탐지
  checkpoint.json        # 현재 상태/예산 원장, 원자 교체
  cases/<case_id>/attempt-001/
    solver.log           # 원본 로그
    raw-solution.json    # 존재할 때만 저장
    result.json          # 검증과 최종 상태, 원자 저장
  summary.json
outputs/phase1-solver-benchmark.html
```

- 상태: `PENDING → RUNNING → DONE` 또는 명시적 실패/중단. DONE 내부에서도 유효해/품질/증명을 별도 표시한다.
- 슬롯 시작 전 예산을 예약하고 checkpoint 저장. 15초마다 heartbeat와 관측 상태를 저장하고, 각 슬롯 종료 후 즉시 원자 교체한다. 한 입력의 세 솔버 묶음과 각 규모 종료 때 요약을 갱신한다.
- 임시파일 작성 → flush/fsync → 같은 파일시스템에서 replace; 가능한 환경에서는 디렉터리도 동기화한다. 덮어쓰기 실패 시 이전 정상 checkpoint를 보존한다. 재시작 때 checksum/스키마로 무결성을 확인한다.
- 솔버가 중간 해를 안전하게 내보내는 경우에만 incumbent snapshot을 보존한다. 15초 heartbeat가 탐색 트리 저장을 의미하지 않는다. 중단된 solve는 재시작하며 최대 한 슬롯의 계산을 잃을 수 있다.
- 재개는 완료 슬롯을 건너뛴다. 실패는 숨기거나 성공할 때까지 반복하지 않는다. 인프라 중단만 원인·attempt 번호를 남겨 1회 재시도 가능하며 총 예산에 차감한다. 정답 오류는 코드 수정과 새 run_id가 필요하다.
- manifest/입력/모델/솔버 버전·옵션이 다르면 같은 실험에 이어 붙이지 않는다. 새 run으로 분리하고 비교표에서도 구분한다.
- 누적 실행 예산은 재개해도 초기화하지 않는다. 시작 예약이 있고 종료 기록이 없는 orphan 슬롯은 제한 시간 전부를 보수적으로 차감한다. supervisor 동작 시간은 monotonic clock으로 누적하고 restart 사이의 명시적 정지 시간은 별도로 기록한다.
- 일시 중단이 있으면 달력상 종료는 하루를 넘을 수 있다. **24시간은 재개를 합친 활성 sweep 예산**이다. 임의 프로세스/사용자 작업을 종료하지 않는다.
- 각 단계 끝에 git 변경·구현 상태·정확한 재개 명령·최근 checkpoint를 `docs/phase1-checkpoint.md`에 기록한다. 실행 자동화는 독립 로컬 CLI로 만들며 대화 토큰이 끝나도 파일에서 재개할 수 있게 한다. 호스트 절전·세션 종료에도 계속 돈다는 보장은 하지 않는다.

즉시 정지 조건: 입력/모델 해시 불일치, 검증기 자체 오류, checkpoint 손상/저장 불가, 디스크 부족, 반복 OOM, 총 예산 소진. 솔버별 무해·시간초과는 실패 결과를 기록하고 다른 후보를 계속한다. 강제 종료 또는 미완성 일정은 `PARTIAL`로 보고하며 완료로 포장하지 않는다.

## 8. 구현 순서와 완료 조건

1. **검증 계약 보강**: 누락/비유한/분수/범위 이탈/상태 오판 회귀 테스트를 먼저 작성한다. 기존 API 응답과 Phase 0 결과를 유지한다.
2. **공통 모델 + 어댑터**: CBC 기준 회귀 후 HiGHS/SCIP 연결, 라이선스·버전 고정, 정답 대조. 지원하지 않는 설정은 조용히 무시하지 않는다.
3. **입력·일정 생성**: 48개 입력과 manifest 동결, hash/불변성/산술 검증. 파일럿 이후 모델 수정 시 새 실험 버전을 만든다.
4. **감독자·체크포인트**: timeout·메모리·kill/restart·디스크 오류·남은 예산 부족을 가짜 worker로 테스트. 실제 24시간을 기다려 복구 기능을 검증하지 않는다.
5. **짧은 end-to-end 점검 → 장기 스윕**: 전체 경로가 통과한 뒤만 실행. 결과 선택 없이 사전 일정대로 진행한다.
6. **근거 보고서**: raw 로그/재현 명령/실패 포함 JSON 및 HTML. 잠정 추천·비용·한계를 함께 기록한다.

구현 완료와 실험 완료를 분리한다. 테스트가 통과했다고 357회 실행 완료를 뜻하지 않으며, 실험이 끝났다고 인력 추천의 사업 효과 검증 완료를 뜻하지 않는다.

### 설계 자체 점검

- 같은 문제를 비교하는가: 입력·계수·pair·옵션 동결, 공통 builder, 해시 대조.
- 음수 점수·시간제한 해를 공정하게 다루는가: 부호 안전 gap, native 상태, 독립 검증.
- 시간이 맞는가: 357슬롯, 79,650초 + 6,750초 = 86,400초.
- 토큰/프로세스 중단 후 재개되는가: 파일 기반 상태·attempt 이력·예산 예약과 보수적 복구.
- 실데이터 부재를 숨기지 않는가: 합성 한정 추천, 사업 검증 NOT_CALIBRATED 유지.
- 남은 불확실성: 각 패키지의 실제 설치 가능 버전, native bound 추출, 300명 모델 생성 시간/메모리. 구현 및 파일럿에서 확인하고 실패도 보고한다.
