# 기술 점수(S) 계산 방식 유지 근거 (보고서용 요약)

- 결정 2026-10-12 · 사용자 결정("그대로 가되 이렇게 간 근거만 작성하자") · 정리 claude-a
- 모든 데이터는 가상(seed 고정)이고 사업 효과는 `NOT_CALIBRATED`다. 이 문서는 "어느 계산식이 현실에서 더 좋은 팀을 만드는가"에 대한 주장이 아니라,
  **그 주장을 지금 할 수 없어서 현재 방식을 유지한다**는 기록이다.

## 결론
**기술 점수는 지금 방식(경력 개월 → 대리 레벨 → 레벨 비율)을 유지한다.**
2026-10-05에 제안된 "경력 개월 비율을 직접 쓰기"(`min(보유 개월 ÷ 요구 개월, 1)`)는 이 시제품 단계에서 채택하지 않는다.
실데이터의 과거 성과가 쌓이면 다시 검토할 항목으로 남긴다(아래 "다시 검토할 때").

## 두 방식
| | 지금 방식(유지) | 제안(채택 안 함) |
|---|---|---|
| 기술 하나의 충족도 | `min(보유 레벨 ÷ 요구 레벨, 1)` | `min(보유 개월 ÷ 요구 개월, 1)` |
| 레벨 | 경력 개월을 구간으로: 12개월 미만 1 · 12~35 2 · 36~59 3 · 60~95 4 · 96 이상 5 (`core/ingest/convert.py::level_from_months`, 경계는 사용자 확정 2026-10-05). 요구 경력도 같은 구간 | 없음(개월 그대로) |
| 프로젝트별 S | 요구 기술들의 충족도를 가중 평균(`core/scoring/engine.py::skill_matrix`, 가중치 기본 모두 3) | 같음 |

두 방식 모두 같은 입력 처리를 거친다: 최근 10년(120개월 상한, 10년 안에 안 쓴 기술 제외) · 기술 이름 사전 · 하위 기술 70% 인정(쓸 경력 = max(본인, 인정분), `core/ingest/skills.py::person_skill_months`).

### 숫자로 본 차이
| 요구 경력 | 보유 경력 | 지금 방식 | 개월 직접 |
|---|---|---|---|
| 36개월 | 35개월 | 0.67 (레벨 2÷3) | 0.97 |
| 36개월 | 36개월 | 1.00 | 1.00 |
| 36개월 | 12개월 | 0.67 | 0.33 |
| 24개월 | 12개월 | 1.00 (둘 다 레벨 2) | 0.50 |
| 60개월 | 35개월 | 0.50 (2÷4) | 0.58 |
| 60개월 | 36개월 | 0.75 (3÷4) | 0.60 |

차이는 두 가지다.
1. **계단**: 지금 방식은 같은 구간 안의 차이를 보지 않고(13개월 = 35개월) 경계에서 한 단계가 통째로 바뀐다(35 → 36개월에 0.67 → 1.00).
2. **곡선 모양**: 레벨 구간은 뒤로 갈수록 넓어서(12 → 24 → 24 → 36개월) 지금 방식은 **큰 부족분에 너그럽다**. 개월 직접 방식은 부족한 비율만큼 그대로 깎는다.
   "요구 3년 자리에 1년차를 넣으면 몇 점이어야 하나"는 계산이 아니라 인사 운영 원칙의 문제다.

## 왜 실험으로 정하지 않았나
- **가상 데이터에는 이 질문의 정답이 없다.** 가상 과거 성과는 생성기의 숨은 규칙으로 만든다(`core/ingest/org_profile.py::_past_outcomes`). 재료는
  숨은 실력, 팀원 간 이전 협업, 같은 산업 경험이 있었는지, 중도 이탈, 고객별 편차, 운이다.
  **기술 경력이 요구 경력을 얼마나 채웠는지는 이 규칙에 없다.** 두 방식을 이 성과와 대조하면 나오는 차이는 우연이다.
- **성과 규칙에 경력을 넣으면 답을 정해 놓은 실험이 된다.** 넣은 모양을 닮은 계산식이 이긴다. 이것은 이 프로젝트의 "결과 맞추기 금지" 원칙에 어긋나고,
  팩터 실험실에서 이미 같은 순환을 확인했다(`docs/model-roadmap.md` 2번: 같은 팩터로 만든 성과 가정에서의 우위는 순환이었다).
- **선례**: 익숙한 쌍 감점(μ)도 가상 성과 대조로는 판단할 수 없어(`rehearsal/results/outcome-check.html`) 운영 원칙으로 넘겼다.
- 가상 데이터로도 잴 수 있는 것(바꾸면 배치가 몇 자리 달라지는지, 경계 근처 기록 오차에 얼마나 흔들리는지, 풀이 시간)은 "얼마나 달라지나"이지
  "어느 쪽이 맞나"가 아니다. 결정에 필요하지 않아 이번에는 재지 않았다.

## 왜 유지인가
1. **바꿀 근거가 없다.** 우열을 실험으로 가릴 수 없고, 사업 효과를 검증하지 않은 시제품이라 바꿔도 "더 좋아졌다"고 말할 수 없다.
2. **바꾸는 비용이 크다.**
   - 공유 계약 `Person.skills`·`SkillRequirement`를 개월 단위로 확장
   - 요구 레벨(`min_level`)을 읽는 코드 전부: 점수 엔진(`core/scoring`), 지표(`core/optimize/metrics.py`), 근거 색인·검색(`core/graph/sqlite_store.py`, `core/rag`),
     지식 그래프·소명 글(`core/kg`), 교체 설명 문맥(`api/rag/context.py`), 가상 생성기(`core/datagen`), Phase 0 오라클·벤치 시나리오 + Phase 0 재검증
   - 시연 미리 계산 6개 재생성(약 40분), 시연 대본·최종 보고서 숫자
   - 화면·PDF·인사팀 소명 글·교체 설명의 "레벨" 표기와 인정 경력 표기
3. **표기가 한 언어로 맞춰져 있다.** 화면·PDF·소명 글·교체 설명이 모두 "요구 레벨 3에 레벨 2"처럼 레벨로 말한다. 점수만 개월로 바꾸면 보이는 근거와 계산이 어긋난다.

## 알려진 한계 (보고서·시연에서 그대로 말한다)
- 같은 구간 안의 경력 차이는 점수에 드러나지 않는다(13개월과 35개월이 같은 레벨 2).
- 경계 근처에서는 몇 개월 차이나 기록 오차로 한 단계가 바뀐다(요구 36개월 자리에 35개월 0.67, 36개월 1.00).
- 요구 12개월과 24개월이 같은 레벨 2라서, 24개월을 요구한 자리의 12개월 보유자도 완전 충족(1.00)으로 본다.
- 구간 경계(12/36/60/96개월)와 레벨 비율이라는 모양 자체가 근거 없는 설계값이다(`NOT_CALIBRATED`).
