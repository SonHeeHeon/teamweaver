## 0. 준비 (전날)
1. `scripts/run_poc.sh`로 한 번 띄워 화면·PDF가 되는지 본다(처음이면 웹 빌드·Chromium 설치까지 몇 분).
2. **미리 계산**: `TEAMWEAVER_SOLVER_SEEDS=4 uv run --group benchmark python -m rehearsal.precompute_demo`(약 40분, 시연 기기에서).
   관리자 설정을 바꾸면 다시 돌린다. 서버를 띄운 뒤 데이터 탭(또는 `GET /api/datasets/active`)의 `precomputed.skipped`가 비어 있는지 본다.
3. `.env`의 LLM 키 확인(AI 설명·리뷰 글 판정). 없으면 설명이 규칙 기반으로 나온다 — 장면 4는 `rehearsal/results/guard-demo.html`로 대신한다.
4. 브라우저 탭 셋: 앱(`http://127.0.0.1:8000`), `docs/architecture.html`, `rehearsal/results/guard-demo.html`.
5. 업로드 장면 파일: `demo/org-n100-broken.zip`. 관리자 로그인 상태로 시작한다.

## 1. 무엇을 만들었나 (1분) — `docs/architecture.html`
- 말할 것: "직원과 사업을 **기술 적합(S)·서로 맞는 정도(C)·월별 가용률·월 예산·등급 정원**을 한꺼번에 맞춰 배치합니다.
  수학 최적화(MILP)로 풀고, 솔버가 낸 답을 **원자료로 다시 검사**한 뒤에만 화면에 냅니다. AI 설명은 동료 평가를 **원문과 대조**해 지어낸 근거를 막습니다."
- 숫자: 시험 1384개, 정답 대조(Phase 0) 11건 통과, 100/200/300명 리허설.

## 2. 연초 계획: 100명 전원 배치 (3분)
- 누를 것: 데이터 탭 "시연 데이터 고르기"에서 `org-n100 · 연초 계획(백지 배치) · 100명 · 사업 20건`이 켜져 있는지 → 요건 설정 → **최적화 실행**.
- 보이는 것: What-if 대시보드로 넘어가며 Plan A~D 카드(최적화율·충족률·배치 수, 계산 신뢰도 배지). 리허설(2026-10-07) 배지:
  안 A "독립 검증 통과 · 시간 한도 도달 · 최적값이 이 해보다 최대 8.9% 높을 수 있음", 안 B~D "다양성 조건의 최적값이 이 해보다 최대 11% 높을 수 있음".
  말할 것: "솔버가 증명한 상한과의 거리를 그대로 보여 줍니다 — 30초 안에 낸 해가 최적에서 얼마나 떨어져 있을 수 있는지까지."
  미리 계산이면 즉시 뜬다(리허설 0.3초). ⏳ 지금은 카드 오른쪽에 "캐시"로만 보인다 — "미리 계산한 결과(같은 데이터·같은 설정)"라고 말로 밝힌다.
- 말할 것: "안 A가 최선이고, B~D는 A와 사람 구성이 충분히 다르면서 품질이 A의 95% 이상인 대안입니다. 조건을 만족하는 대안이 없으면 억지로 채우지 않습니다."
- 숫자(서비스 설정, 시드 4, `demo/precomputed/org-n100.json`): 안 A~D 모두 빈자리 0, 목적 59.43 / 58.21 / 58.53 / 58.23, 실시간이면 약 2분(30초×4, 모두 시간 한도에서 멈춘 최선 해).
- 막히면: 미리 계산이 버려졌으면(설정 변경 등) 2분 걸린다 — 그동안 장면 3 숫자를 말한다.

## 3. 사람이 엑셀로 짜면? 단순 규칙 대비 (1분)
- 누를 것: What-if 대시보드의 "단순 규칙(기술 1등 우선) 대비" 카드 → **단순 규칙과 비교**.
- 같은 데이터·같은 평가 기준으로 "자리마다 기술 1등부터 넣기"와 비교(`rehearsal/results/baseline-check.json`).

| 인원 | 배치 품질(최적화 / 단순 규칙) | 협업 | 빈자리 | 제약 위반 |
|---|---|---|---|---|
| 100 | 58.2 / 31.6 | 19.8 / 1.0 | 0 / 1 | 0 / 0 |
| 200 | 109.6 / 66.0 | 20.9 / 0.7 | 0 / 1 | 0 / 예산 1 |
| 300 | 164.0 / 113.5 | 27.4 / 0.7 | 0 / 3 | 0 / 예산 2 |

- **정직하게 함께 말할 것**: 자리당 평균 기술 적합은 단순 규칙이 높다(0.76 대 0.64). 최적화는 정원에 없는 등급을 예산 안에서 더 넣어 전체 기여를 늘리기 때문이다.

## 4. 교체 검토 + AI 설명 + 지어낸 근거 막기 (3분)
- 누를 것: What-if 대시보드 → "인력 교체 (What-if)"에서 교체 대상·교체 투입 고르기 → **브리핑 생성**(LLM, 리허설 약 20초).
- 보이는 것: 교체 전후 점수(**참고값** — 재최적화가 아니라 같은 목적·제약으로 다시 채점), 위반 경고, AI 설명(동료 평가 직접 인용 + 출처 배지).
- 이어서 `guard-demo.html`: 같은 질문에 미리 정해 둔 AI 답 세 개 → 원문 그대로 인용은 채택, **한 단어 바꾼 인용**과 **없는 출처**는 거절 → 규칙 기반 설명으로 전환.
- 말할 것: "AI가 근거를 지어내면 화면에 나가지 않습니다. 실제 회사 데이터에서는 평가 원문을 화면·AI 설명에 보내지 않고 항목 라벨만 씁니다."

## 5. 운영 중 편성: 대기 10명으로 신규 제안 2개 (4분)
- 누를 것: 데이터 탭 → 시연 데이터 `org-n100-operating · 운영 중 …` → **이 시연 데이터로 전환 → 전환 확인** → 운영 중 편성 탭 → **K별 비교 실행** → K=1 **이동 보기**.
- ⏳ 미리 계산이면 즉시 뜨는데, 표의 "시간"(0.4초·1.0초·11.9초·18.8초)은 미리 계산 때의 풀이 시간이다. 배지가 생기기 전에는 반드시 말로 밝힌다.
- 말할 것: "평소 장면은 대부분 이미 일하는 중이고, 막 끝난 몇 명으로 새 사업을 짜는 겁니다. 기존 배치를 **최대 K명까지만** 바꿀 수 있게 하고, K별로 얼마나 좋아지는지 보여 줍니다."
- 숫자(화면과 같은 데이터 = 리뷰 글 LLM 판정, `demo/precomputed/org-n100-operating.json`, 모두 최적 증명):

| K(옮기는 사람 수) | 0 | 1 | 2 | 3 |
|---|---|---|---|---|
| 빈자리 | 2 | 1 | 0 | 0 |
| 배치 품질 | 69.05 | 69.77 | 69.56 | 70.23 |
| 계산 시간(실시간이면) | 0.4초 | 1.0초 | 12초 | 20초 |

- 이야기: 대기 10명에 초급이 없어 K=0이면 신규 제안의 초급 자리가 빈다. K=1이면 DP0013(중급)을 J005에서 빼 신규 제안 J014·J015에 나눠 넣고, 빠진 자리를 대기 인력 DP0041이 메운다. K=2면 두 사업 사이 맞교환으로 빈자리가 사라진다(품질은 K=1보다 0.2 낮지만 빈자리 하나를 메운 쪽이 총점이 높다).
- (참고) `rehearsal/results/operating-check.json`은 리뷰 글을 항목 균형으로 판정한 측정이라 숫자가 조금 다르다(K=0 품질 69.19, K=1의 대기 인력 DP0088).
- 주의: 옮긴 사람은 반드시 "원래 없던 사업"으로 간다(빼서 놀리는 해를 막는 규칙). 잠근 사람은 옮기지 않는다.

## 6. 사업 보강 시뮬레이터 (3분)
- 누를 것: 운영 중 편성 탭 아래 "진행 사업 보강" → 사업 `[실행] 금융사 파2 비정형 데이터 마트 구축(J007)` → **후보 보기** → "넣어 보기" → 최선 n명 **최선 조합 계산**.
- 숫자(화면 = 리뷰 글 LLM 판정 데이터, 리허설 2026-10-07): 1위 DP0032(대기 인력·중급) +1.05 — 기술 적합 0.80, 팀 협업 3.50, 익숙한 쌍 0;
  2위 DP0046 +0.91 — 익숙한 쌍 −0.20이 순위를 낮췄다. 후보 순위 100명 약 2초.
- (참고) 항목 판정 측정(`rehearsal/results/operating-check.json`)에서는 1위가 DP0046(+1.06)이었다 — 리뷰 글 판정 방식이 협업 점수를 바꾼다.
- 말할 것: "다른 사업에서 빼 오면 그 사업에 생기는 빈자리까지 같이 계산합니다."

**운영 중 묶음에서는 요건 설정의 "최적화 실행"(전원을 처음부터 다시 짜기)을 누르지 않는다.** 진행 사업의 정원·예산이 지금 명단에 맞춰져 있어
200·300명은 시간 한도 안에 빈자리가 남는다(미리 계산 기록 `org-n200-operating`·`org-n300-operating`의 안 A~D). 운영 중 장면은 K 비교로 보여 준다(같은 데이터에서 빈자리 0, 32~101초).

## 7. 실데이터 연결 준비: 일부러 틀린 파일 (2분)
- 누를 것: 데이터 탭 → 파일 선택 `demo/org-n100-broken.zip` → **검증 후 전환**.
- 보이는 것: 오류 6건 — people.csv 2행 등급 빈칸, person_skills.csv 1행 '열두달', availability.csv 3행 1.5(>1), reviews.csv 1행 없는 사람 XX9999,
  current_assignments.csv 2행 중복, projects.csv 2행 종료<시작. **검증을 통과하기 전에는 계산 데이터가 바뀌지 않는다.**
- 화면은 "전환하지 않았다 — 검증 오류가 있어 전환하지 않았다"와 오류 목록을 보인다(오류 문장은 영어 원문 — 말로 풀어 준다).

## 8. 300명 규모 (2분) ⏳
- 누를 것: 데이터 탭 → 시연 데이터 `org-n300 · 연초 계획 …` → 전환 확인(리뷰 글 판정 캐시가 있으면 약 15초) → 요건 설정 → **최적화 실행**(미리 계산이면 1~2초).
- 보이는 것: 안 A "시간 한도 도달 · 최적값이 이 해보다 최대 3.6% 높을 수 있음"(서비스 한도 180초에서 멈춘 해, 목적 166.41, 빈자리 0),
  안 B~D "다양성 조건 · 허용 차이 5.0% 안에서 최선 증명"(한도 전에 목표 갭 도달). ⏳ 미리 계산 배지는 화면 작업 중 — 말로 밝힌다.
  **"다시 계산"은 누르지 않는다**(안 A~D 약 7.7분, `demo/precomputed/org-n300.json`).
- 말할 것: "시드 4개를 동시에 돌려 가장 좋은 해를 고르고, 솔버가 증명한 상한과의 거리를 함께 기록합니다. 미리 계산한 결과는 같은 데이터·같은 설정일 때만, 지금 평가기로 다시 채점해 맞을 때만 씁니다."

## 9. 왜 믿을 수 있나 (1분)
- 솔버 답을 원자료로 다시 검사(독립 검증) — 정수성·범위·제약·목적값. HiGHS가 돌려주는 1.0000000000000007 같은 값도 여기서 걸렀다.
- 정답 대조(Phase 0): 작은 사례 11건을 전수 탐색 정답과 비교(갭 0).
- 규칙 결정은 측정으로: "익숙한 쌍" 기준을 세 가지로 비교해 '최근 3년 중 12개월'로 정했다(`rehearsal/results/rule-compare.html`).

## 10. 한계 (1분)
- 사업 효과는 실제 성과 데이터가 없어 검증 전이다. 실데이터가 오면 같은 점검 도구(`core/evaluate/outcome_check.py`)로 "모델 가정이 과거 성과와 맞는지"를 본다.
- "오래 붙어 다닌 사이" 감점은 문헌이 두 갈래다(`docs/demo-notes.md` 7절). 감점 크기·기준은 설계값이다.

## 막혔을 때
| 증상 | 대처 |
|---|---|
| 데이터 탭에 "기본 데이터로 시작했다" 경고 | 시연 묶음을 못 읽었다 — 목록에서 다시 고르거나 `run_poc.sh` 재실행 |
| 계산이 오래 걸림 | 데이터 탭 `precomputed.skipped` 확인(설정을 바꿨으면 미리 계산이 버려진다 → 설정 되돌리기) |
| AI 설명이 규칙 기반으로만 나옴 | LLM 키·네트워크 문제. 정상 동작이다 — `guard-demo.html`로 장면 4 보충 |
| PDF 실패 | `cd web && npm run build`, `uv run playwright install chromium` |
