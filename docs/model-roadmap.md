  "최선임을 증명하지 못한 답"이 나온다. 문제는 그 답이 최선과 얼마나 떨어져 있느냐다.

3. 설정 화면: `time_limit` 상한을 측정 근거로 올리고, 인원 구간별 기본값(자동)과 관리자 수정값을 둔다.
   화면에 "시간 한도 도달 — 최선임을 증명하지 못한 답" 표시. 대안 B~D까지 고려한 총 대기 시간도 안내.
4. HiGHS 서비스 연결(K3)과 함께 하면 같은 시간에 더 좋은 답을 기대할 수 있다(리허설 수치로 확인).

## 2. 좋은 모델(방정식) 찾기

**지금 모델의 한계**: 목적식은 기술 적합도(S) + 0.3·협업 궁합(C) − 0.2·반복 협업 − 100·미충원. 계수는 설계값이고,
팩터가 기술 수준·협업 기간·리뷰 점수뿐이다. 경력의 깊이·최근성, 도메인·고객 경험, 업무 부하 균형,
연속성(이미 투입 중인 사람), 등급 적합도, 성장(주니어 배치) 같은 팩터가 없다.

**주의(정직성)**: 가상 데이터에는 "실제로 잘 된 팀"이라는 정답이 없다. 우리가 만든 생성기에 맞춰 계수를 고르면
그 생성기의 가정을 되찾을 뿐이다. 그래서 가상 단계의 목표는 "최적 계수 발견"이 아니라
**(a) 팩터 후보를 넣고 빼는 실험 장치**와 **(b) 성과 시뮬레이터(가정 명시)를 바꿔도 순위가 안정한 팩터 조합 찾기**,
**(c) 실제 성과 데이터가 들어오면 같은 장치로 바로 보정**할 수 있는 준비다.

**할 일**: 팩터 카탈로그 → 성과 시뮬레이터(여러 가정) → 팩터 조합·계수 탐색(교차 검증) → 민감도 보고서.
기록: 이 문서 + 실험 결과 보고서(시연용 "처음 모델 vs 개선 모델" 비교).

## 3. 특이한 프로젝트에서도 안정적인 점수

**의심 지점(점검 대상)**: 요구 기술이 1개인 프로젝트와 10개인 프로젝트의 S 평균 방식, 대형 프로젝트(예: 내부 28명 + 외주 다수인
AI 에이전트 공동 사업)가 점수를 독식하는지, 1~2개월 제안 프로젝트, 요구 기술이 없는 프로젝트, 예산이 빠듯한 프로젝트,
희귀 기술 요구, 등급 미기재.

**할 일**: 특이 프로젝트 유형 카탈로그(리허설 생성기에 포함) → 프로젝트별 점수 분포·배치 결과 이상치 점검 →
정규화(프로젝트 크기·요구 수 보정 등) 수정 → 수정 전후 비교를 시연 자료로.

### 발견한 모델 빈틈 (2026-10-05, 팩터 실험실 준비 중)
- **기존 투입 연속성 없음**: 실제로는 실행 중인 사업에 이미 들어가 있는 사람이 많은데, 현재 MILP는 6개월 계획의 모든 자리를
  백지에서 다시 짠다. 그 결과 "이미 잘 돌아가는 팀을 흔드는" 배치가 나올 수 있다. 현 투입 명단을 입력으로 받아
  유지 보너스(또는 변경 비용)를 두는 팩터·제약이 필요하다(실데이터 입력 계약에 "현재 투입" 칸 필요 — 업무이력의 진행중 행으로 대체 가능).

## 4. 부서별 모델 맞춤

**구상**: 부서별 "모델 프로필"(팩터 선택·계수·규칙)을 버전으로 관리한다. 설정 화면의 보정 마법사에
과거 프로젝트 성과 이력 + 당시 기술 이력·피어리뷰(시점별 버전)를 넣으면 2번 장치로 후보 모델을 만들고,
현재 모델과 나란히 비교한 뒤 관리자가 승인해야 적용한다.

**판단**
- 갱신 주기: 연 1회 고정보다 **피어리뷰 주기(반기)에 맞춘 점검 + 성과 데이터가 일정량 쌓였을 때 재보정**을 권한다.
  재보정은 자동 적용하지 않고 비교 보고서 → 승인 순서. 모델이 바뀌면 이전 버전으로 되돌릴 수 있어야 한다.
- 솔버: **하나로 고정이 맞다.** 솔버는 "어떤 답이 좋은가"가 아니라 "같은 식을 얼마나 빨리 푸는가"의 문제라 부서별로
  다를 이유가 없다. 다만 모델 식이 크게 바뀌거나 규모가 커지면 그때 다시 비교한다(Phase 1 장치 재사용).
- 데이터 요건: 프로젝트별 성과 지표의 정의가 먼저 필요하다 — 사용자·현업 결정 사항.
  후보(스키마 양식 답변상 회사에 **있음**, 아직 확보 전): 고객 평가 기록, 고객 요청 인력 교체와 그 사유(부정 신호), 같은 고객의 후속·고도화 과제(긍정 신호).
