# TeamWeaver 프로젝트 맥락 요약 (2026-10-03, 소스 기준 `0bc4c7c`)

개발 착수 전 읽는 압축본. 원본은 `outputs/eli5-project-history-roadmap.html`(18장, 비전문가용).
여기의 수치는 기록 시점 값이며 다시 측정한 값이 아니다. "현재 구현"·"과거 관측"·"제안"을 구분해 적었다.

## 1. 문제와 목표

- 같은 조직 개발자를 여러 실행·제안 프로젝트에 나눠 배치할 때, 기술·협업 이력·월별 가용률·
  등급 정원·월 예산을 함께 계산하고 근거와 대안을 보여주는 의사결정 보조 도구. 최종 결정은 사람이 한다.
- 기준 데모: 가상 100명 × 20프로젝트 × 6개월(`fixtures/`, seed 42, 리뷰는 LLM 생성·파싱 266건).
- 초기 정책 목표 "최적화율 90%"는 정책 지표이며 고객 만족 90%를 뜻하지 않는다.
- LLM은 배치를 정하지 않는다. 자유서술 리뷰를 숫자로 바꾸고, 설명문을 쓸 때만 쓴다.

## 2. 현재 시스템 흐름 (현재 구현)

fixture JSON → API 부팅 시 임시 SQLite(근거 검색) + MemoryGraph(S/C 계산) → CBC MILP →
`/api/optimize` SSE로 A안부터 순차 전달 → 웹(가중치 슬라이더·후보 카드·협업 그래프·드래그 교체)
→ `/api/whatif`(교체 전후를 MILP 전체 목적·제약으로 재평가한 참고값과 새 위반·미충원 + LLM 브리핑, 실패 시 규칙 기반 fallback) → `/api/report`(Playwright PDF).

- 고정 JSON만 읽는다. CSV import·HR API·인증·작업 큐·영구 저장 없음.
- 캐시 키는 weights/milp_params/대안 수뿐(데이터 버전 없음). 기본 시나리오는 부팅 시 사전 계산(~28.5초).
- PDF 명단은 원래 선택 플랜이다. 검토한 교체가 반영된 확정안이 아니다.

## 3. 모델 (현재 구현)

목적: `Σ S_ij·a_ij + 0.3·Σ C_pq·y_pqj − 0.2·Σ_{반복협업쌍} y_pqj − 100·Σ slack_jg` 최대화.
계수는 설계값이며 실제 성과로 보정하지 않았다.

| 변수 | 의미 |
|---|---|
| `z[i,j]` | 배치 여부(0/1) |
| `a[i,j]` | 투입률. 배치 시 0.2~1.0, 프로젝트 기간 내 일정 |
| `y[p,q,j]` | 두 사람 동시 배치(선형화). 보상쌍 = \|C\| 상위 15%·최대 5,000 절삭, 감점쌍 = 협업 6개월 이상 전부 |
| `slack[j,g]` | 등급 정원 미충원(큰 감점, 출력에 노출) |

- 하드 제약: 월별 Σa ≤ 가용률, 월 예산 Σ(단가·a) ≤ 예산, 기재 등급별 Σz + slack = 요구 인원.
- S: 요구 기술별 `min(보유/요구, 1)`을 1~5 가중치로 평균(미지정 가중치 3).
- C: `0.4·min(협업개월/12, 1) + 0.6·리뷰점수`, 리뷰점수 = 0.5·체크항목 균형 + 0.5·텍스트 극성. [-1,1]로 자름.
- 대안: 이전 모든 플랜의 (사람,프로젝트) 쌍 중 최대 80%만 재선택하는 컷을 넣어 재풀이.
  품질 하한 `alt ≥ A − 0.05·|A|`(부호 대칭). A안은 gap 1%, 대안은 기본 5%. 조건 미달 시 대안이 3개보다 적을 수 있다.
- 알려진 모델 공백: 필수 기술 하드 제약 없음 · 미기재 등급 무제한 · 월별 가변 투입 없음 ·
  리뷰에 project/date/review_id 없음(같은 방향 중복 리뷰는 dict에서 마지막 것만 남음).

## 5. 실험 결과 요약 (과거 관측)

- 실험 1(관계 탐색 50~1,000명×1~4hop): 메모리 < SQLite < Neo4j. Neo4j 역전 가설 기각.
- 실험 2(Full-LLM vs Hybrid): 입력 토큰 31.4% 감소. 비용 절감폭은 출력량 가정에 따라 31.4%~0.78%.
  정확도·지연은 미측정. "80% 절감"은 입증되지 않음.
- 실험 3(Greedy vs MILP, template 데이터): MILP 최적화율 50/10 0.917, 100/20 0.928, 200/40 0.885(목표 미달).
  Greedy ~0.67~0.72. 300명 이상은 미측정.
- 실험 4·5(설명용 질의 5종, 적재·갱신·디스크·재수화): Neo4j 우위 0/20, 0/4.
  실험 4 첫 스윕 원시 데이터는 덮어쓰기로 유실됨.
- 웹 데모(LLM fixture 100/20): 최적화율 ~0.9300, 기술 충족률 ~0.5476, 미충원 0, MILP가 Greedy(~0.71)보다 높음.
  주의: 실험 3의 100/20(template 리뷰)과 데모 100/20(LLM 리뷰)은 C가 달라 서로 다른 데이터다.

## 6. Phase 0 — 계산 구현 검증 (`experiments/bench/phase0_model.py`)

- 소형 정답기(`experiments/phase0/oracle.py`)는 사람 선택 조합을 완전 열거하고 SciPy LP로 투입률을 푼다.
  제품 MILP의 제약 객체를 읽지 않는다.
- 11개 점검: 정답 대조 7/7 차이 0, 단조성 2/2, pair 절삭 손실 ~0.0105%(해당 입력 한정), 50/10 smoke
  (변수 2,861·제약 6,831, ~0.67초).
- `core/optimize/validation.py::validate_raw_solution`은 a/z/y/slack의 결측·NaN·범위·이진성, 가용률·예산·
  등급, pair 범위, 목적 4항을 재계산한다. 검증할 수 없는 값을 0으로 채우지 않는다.
- 전체 runner 기한 240초, 케이스마다 원자적으로 체크포인트를 저장한다.

## 7. Phase 1 — 오픈소스 솔버 비교 (`experiments/phase1/`)

- 같은 입력·S/C·pair·계수를 CBC(PuLP 번들)·HiGHS(highspy 1.15.1)·SCIP(PySCIPOpt 6.2.1)에 준다.
  1스레드, 직렬 실행, 매번 새 프로세스, warm start 없음, 내부 gap 0 요청, 케이스당 최대 240초.
- 일정 357칸: 오라클 21, 호환성 3, 파일럿 9, 본평가 288(4규모×4조건×3seed×3솔버×2반복),
  300명 재확인 36. 조건: baseline, availability_pressure, budget_pressure(예산 15% 축소), dense_collaboration.
- 모듈: `scenarios.py`(입력 동결·해시) · `schedule.py` · `solvers.py`(어댑터, 0/1 경계 1e-6 정규화) ·
  `runner.py`(감독자: heartbeat, 예약, RSS 12GiB 감시, 프로세스 그룹 정리) · `worker.py` ·
  `checkpoint.py`(원자 저장·매니페스트 해시) · `report.py`(HTML).
- v2 결과: DONE 197 / NO_VALID_INCUMBENT 87 / DEADLINE_EXCEEDED 68 / ORPHANED_ACKNOWLEDGED 5
  (감독자가 완료를 확인하지 못한 중단 건은 성공에서 빼고 240초씩 차감). 활성 시간 약 10시간 15분.
- 오라클을 뺀 솔버당 112건 기준: HiGHS 79(전부 QUALITY_PASS, 완료 건 중앙 6.61초) · SCIP 75(7.52초) ·
  CBC 22(1.00초, 신뢰할 상한이 없어 BOUND_UNKNOWN, 생존 편향). 본평가와 재확인만 세면 분모는 108이다.
- 300/60 완료는 HiGHS 6/37, CBC 3/37, SCIP 0/37이며 전부 availability_pressure 조건이었다.
  이 규모는 서비스 준비가 안 된 상태다. 200/40에서 SCIP 완료 건의 중앙 시간은 234.6초로 한도에 근접한다.
- 품질 gap = `max(0, U−L) / max(1, |U|, |L|)`. QUALITY_PASS = 독립 검증 통과 + 기한 내 + gap ≤ 5%.

## 8. 남은 작업 (현행 코드 확인 결과 + 제안 로드맵)

로드맵 순서. 앞 단계가 뒤 단계의 비교 기준이 되므로 순서가 중요하다.

0. 현재 증거 보존: 357건 원시 결과·해시를 묶어 보관할 경로를 정한다(423MB, Git 밖).
1. 같은 동결 모델로 Gurobi 비교: 30일 상용 평가판이 필요하다(무료 크기 제한판은 변수·제약 2,000개라 50/10도 못 푼다).
   모델을 먼저 바꾸면 솔버 효과와 수식 효과가 섞이므로 이 단계가 먼저다.
2. 실제 컬럼 의미와 배치 규칙 확정: 필수/선호 기술, 허용 등급, 최소 투입, 가용률 산식, 비용 단위.
3. CSV 수집·검증·가상 데이터 생성: 파일 묶음 A~H(people, person_skills, availability, projects,
   grade/skill_requirements, coworks, reviews+review_items, taxonomy+manifest) → 정규화 → 스냅샷.
   결측을 몰래 0이나 100%로 바꾸지 않는다.
4. 모델 개선(필수 기술·등급 정책 → Phase 0 재검증)과 300/60 병목 실험. 한 번에 한 요인씩
   (후보 축소, 관련 pair만 생성, warm start, 분해, 예산 인지 Greedy).
5. 서비스 연결: HiGHS를 제품 인터페이스로 연결하고, 응답 전에 raw/display 검증을 수행한다.
   What-if 점수 정의·표시 정정은 완료(2026-10-04 K1). 남은 것은 "검토→적용→승인" 흐름 구분이다. 캐시 키에 데이터·모델 버전을 넣는다.
6. 운영 준비: Linux 자원 제한, 큐·취소·동시성, 인증·권한, 감사 원장, 백업.
7. 현실 평가: 승인된 성과 데이터가 있을 때만 한다. 가상 성과로 효과를 입증하는 것은 순환 검증이라 금지다.
8. Shadow mode → 제한 파일럿.

실제 HR 값 없이 지금 바로 할 수 있는 일: 원시 증거 보존 점검, Gurobi 어댑터 계약 설계와 mock 테스트,
CSV 초안과 검증기, 필수 기술·등급 정책 시나리오 문서화. (What-if 계약 정정은 2026-10-04 완료)
