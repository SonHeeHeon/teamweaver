## 결론
**지식 그래프는 프로그램 메모리에 올리는 속성 그래프(in-memory property graph) 방식으로 구현한다.**
- RDF 트리플 저장소, 그래프 데이터베이스(Neo4j), 메모리 그래프(networkx)를 같은 사실·같은 질문으로 비교했다. 사전에 정한 규칙에 따라 **메모리 그래프(networkx)** 가 선정됐다.
- **구현은 현재 `core/kg`를 유지한다**(사용자 결정 2026-10-09). `core/kg`는 networkx가 아니라 파이썬 기본 자료구조로 만든 메모리 그래프다.
  - 방식은 networkx와 같고, 12칸 중 10칸에서 networkx보다 빨랐으며, 의존성이 늘지 않는다.
  - 보고서 문구: "메모리 그래프 방식 채택(비교 실험에서 networkx 후보 선정), 구현은 같은 방식의 자체 경량 구현".
    **"networkx를 썼다"고 쓰지 않는다.**
  - 이 판단은 사전 규칙 밖의 것이다(규칙은 세 후보 중 하나를 고른다). 표준 그래프 알고리즘(중심성·경로 등)이 필요해지면 networkx로 옮기는 비용은 작다.
    적재 47 ms이고, 비교용 어댑터가 `rehearsal/kg_backends.py`에 있다.

## 비교 방법
- **같은 사실**: 시연 연초 계획 묶음 100·200·300명에서 뽑은 지식 그래프(+ 미리 계산한 안 A의 배치)를 썼다.
  - 규모: 노드 328~699개, 간선 9.4천~3.96만 개, RDF로 옮기면 고유 트리플 8.1만~32만 개.
  - 간선 속성(경력 개월 등)은 RDF에서 표준 RDF 1.1 범위의 관계 노드(n-ary) 패턴으로 담았다. 목록 속성은 여러 값 속성으로 담았다.
- **같은 질문 4개**(화면과 인사팀 소명이 실제로 쓰는 것)
  - 조직 기술 지도(전체 집계)
  - 사업별 근거
  - 3단계 탐색(팀원 → 최근 함께 일한 사람 → 요구 기술, 안 A에서 배치되지 않은 사람만)
  - 한 사람 주변 사실 전부(간선의 모든 속성)
- **정확성**: 후보의 답을 정규화해 현재 구현(`core/kg`)과 비교했다.
  - Q2·Q3는 배치가 있는 사업 전부, Q4는 사람 30명을 확인했다.
  - Q4의 목록 속성(평가 항목 등)은 집합으로 비교했다. 순서·중복까지 보는 엄격 비교는 따로 기록했다.
- **공정성**
  - 후보마다 그 기술에 맞는 방식으로 적재했다. Neo4j는 id 고유 제약(색인)과 UNWIND 배치 적재, Oxigraph는 메모리 저장소와 일괄 적재를 썼다.
  - 측정 전에 버리는 예열 회차를 두었다. 질문마다 준비 호출 10회 뒤 20회를 재서 중앙값을 썼다.
  - 첫 작성에서 느렸거나 왕복이 많던 질의는, 같은 답이 나오는 다른 작성법과 비교해 가장 빠른 것을 썼다(세 후보 모두, 상세 보고 5절).
    다른 작성법 질의도 스크립트에 남겨 측정 때마다 다시 잰다.
- **환경**
  - 기기: Apple M4, macOS, Python 3.12
  - 저장소·라이브러리: Neo4j 5.26 community(Docker Desktop, Bolt, 이 실험이 정한 힙 1G·페이지 캐시 512M), pyoxigraph 0.5.11, networkx 3.7

## 결과(300명 기준, 지연 중앙값)
| | 메모리 그래프(networkx) | RDF(Oxigraph, SPARQL) | 그래프 DB(Neo4j, Cypher) |
|---|---|---|---|
| 정확성(기준 구현과 같은 답) | 4/4 | 4/4 | 4/4 |
| Q4 엄격 비교(목록 순서·중복) | 같음 | **다름**(여러 값 속성은 순서가 없다) | 같음 |
| 조직 기술 지도 | 5.7 ms | 7.9 ms | **5.1 ms** |
| 사업별 근거 | **0.24 ms** | 2.0 ms | 1.0 ms |
| 3단계 탐색 | 2.5 ms | 4.3 ms | **1.8 ms** |
| 한 사람 주변 | **0.37 ms** | 9.0 ms | 6.8 ms |
| 적재 | **47 ms** | 733 ms | 1,150 ms |
| 추가 메모리 | **28.5 MB**(파이썬 할당) | 약 160~240 MB(프로세스 메모리 증가, 측정마다 편차 큼 — 하한일 수 있음) | 컨테이너 1.5 GiB(빈 상태 1.3 GiB) |
| 별도 서버 | 없음 | 없음 | 필요(JVM) |
| 디스크 잔류 | 없음 | 없음 | 있음(/data: 빈 DB 516 MB → 적재 후 528 MB) |
| 적재+질의 코드 | 64줄 | 136줄 | 67줄 |

- **셀 승수**(질문 4개 × 규모 3개 = 12칸)
  - RDF와 networkx만 비교: networkx 11, RDF 1
  - 운영 원칙(규칙 3)을 빼고 세 후보를 모두 비교: networkx 8, Neo4j 4, RDF 0. 이 경우에도 networkx가 과반이다.
- **Neo4j가 앞선 칸**: 200·300명의 조직 기술 지도와 3단계 탐색(전체 집계·다단계 탐색)에서는 networkx보다 빨랐다.
- **엄격 비교로 판정해도 같다**: Q4를 순서까지 보는 엄격 비교로 판정하면 RDF가 탈락하지만, 판정은 여전히 networkx다.
- **순수 파이썬 RDF(rdflib)**: 참고로만 쟀다. 300명에서 3단계 탐색 한 번에 209초, 사업별 근거에 66초가 걸려 화면용으로는 쓸 수 없다.
- **현재 구현(`core/kg`)과 networkx 비교**: 현재 구현이 12칸 중 10칸에서 빨랐다(300명 3단계 탐색 0.8 ms 대 2.5 ms 등).
- **메모리 수치의 한계**
  - 파이썬 할당(tracemalloc)은 Rust로 할당하는 Oxigraph를 보지 못한다.
  - 프로세스 메모리 증가(RSS)는 앞서 풀린 메모리를 다시 쓰면 작게 나온다.
  - 그래서 후보마다 맞는 쪽을 표에 적었고, 상세 보고에는 두 값을 모두 적었다.

## 판정 과정(사전 규칙 그대로)
1. **정확성**: 세 후보 모두 4개 질문에서 기준 구현과 같은 답을 냈다. 탈락 없음.
2. **화면 응답성**: 300명에서 200 ms를 넘는 후보가 없었다. 가장 느린 것도 9 ms다. 탈락 없음.
3. **운영 정책**: Neo4j는 별도 서버가 필요해 후순위로 밀렸다. 근거는 두 가지 기존 결정이다.
   - PoC 배포는 "소스 그대로"(2026-10-05)
   - 실데이터를 서버 디스크에 남기지 않는다(K9·K13)
4. **성능**: networkx가 11/12칸에서 이겨 과반이다. → **메모리 그래프(networkx)**
5. **표준 교환**: 외부 표준 형식 교환이나 규칙 추론은 현재 요구사항이 아니다.
   - 표준 형식으로 **내보내야** 할 때는 내보내기로 충족된다는 것을 시험했다.
     - 300명 지식 그래프 전체를 RDF(Turtle) 321,951트리플로 내보내고 다시 읽으면 내용이 같다.
     - 기술 37개를 SKOS 개념 37개로 내보낼 수 있다.
   - 외부 데이터를 합치거나 규칙으로 추론하는 일은 이 시험의 범위가 아니다(아래 "달라질 수 있는 조건").

판정 규칙 코드에는 알려진 차이가 있다. 사전 등록 코드라 고치지 않고, 시험으로 고정해 두었다. 이번 결과(과반)에는 영향이 없다.
- 셀 승수가 동률이고 평균 차이가 10%를 넘으면, 문서("코드 줄 수가 적은 쪽")와 달리 먼저 나열된 후보를 고른다.
- 근소 차 규칙이 과반 후보에도 적용된다.
- 계획의 "의존성" 기준이 코드에 없다.

## 왜 이 결론이 이 시스템에 맞는가(해석)
- 원본은 CSV 묶음이다. 그래프는 데이터가 바뀔 때마다 다시 만드는 **색인**이지, 계속 보관하는 장부가 아니다.
  - 다시 만드는 시간: 사실 추출 약 0.05초 + networkx 적재 약 0.05초(300명). 묶음 읽기·변환은 점수 계산에도 어차피 필요하다.
  - 따로 보관하는 저장소를 두면 CSV와 내용이 어긋날 수 있고, 운영할 서버가 하나 늘어난다.
- 그래프 DB(Neo4j)는 전체 집계와 다단계 탐색에서 메모리 그래프보다 빨랐다.
  - 다만 이 규모에서는 모든 질문이 10 ms 안에 끝나 화면 체감 차이가 없다.
  - 반면 서버·메모리 비용은 계속 든다. 2026년 8월 저장 계층 실험(설명용 질의 5종에서 Neo4j 우위 0/20)과 같은 방향이다.
- RDF는 국제 표준 교환·추론에 강점이 있다. 하지만 간선 속성이 많은 이 데이터에서는 다음이 걸렸다.
  - 표현이 길어진다. 고유 트리플 수가 간선 수의 약 8배다.
  - 목록의 순서를 담으려면 별도 설계가 필요하다.
  - 질의 작성법에 따라 속도가 크게 갈린다. 3단계 탐색은 같은 답의 SPARQL 네 가지가 1.9 ms ~ 80초(100명, 사업 하나 기준)였다. 사업별 근거는 8배 차이였다.
  - 표준이 필요한 곳(기술 이름 사전 등)은 SKOS 구조를 따르는 파일과 내보내기로 충족한다.

## 결론이 달라질 수 있는 조건
- 수만 명 규모, 또는 여러 시스템이 같은 그래프를 동시에 읽고 쓰는 경우 → 그래프 DB를 다시 검토한다.
- 여러 조직·외부 기관 데이터를 표준 형식으로 합치거나 규칙 추론이 핵심 기능이 되는 경우 → RDF 저장소를 다시 검토한다.
- Neo4j 지연에는 macOS Docker Desktop의 가상 머신 포트 포워딩 왕복이 들어 있다. 리눅스 서버에 배포하면 더 짧을 수 있다.
  다만 규칙 3을 빼고 계산해도 결론은 같았다.
- 측정 기기는 하나다. 수치는 기기마다 다르며, 판정은 규칙에 따라 기계적으로 냈다.

## 재현
```
uv run --with pyoxigraph --with rdflib --with neo4j --with networkx --with psutil python -m rehearsal.kg_backends
```
- Docker가 필요하다. Neo4j 컨테이너 `tw-e8-neo4j`를 띄우고, 끝나면 지운다. 약 1시간 걸리며 대부분은 참고용 rdflib 시간이다.
- 비교용 라이브러리는 프로젝트 의존성에 넣지 않았다.
