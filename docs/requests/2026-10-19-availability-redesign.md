## 왜 재설계가 필요한가(claude-b 실측, 시드 4, `rehearsal.precompute_demo`와 같은 설정 경로)
생성기 `core/ingest/org_profile` 연초 계획 가용률을 위 가정(대부분 100%)으로 바꾸고 다시 풀어 봤다(이 커밋에서는 **되돌렸다** -- 데이터·생성기는 지금 main과 같다):

| 데이터 | 시간 한도(안 하나) | 안 A 목적 | 빈자리 항목 | 배치 건수 | 증명 상한 |
|---|---|---|---|---|---|
| 100명 6개월(예전 무작위 가용률, 지금 main) | 30초 | 57.59 | 0 | 121 | — |
| 100명 6개월 새 가용률 | 30 / 60 / 120초 | 28.55 / 79.4 / 79.4 | 0 | 158 | 99.9 |
| 100명 12개월 새 가용률 | 30 / 60 / 120 / 240초 | −8123 / −8123 / 59.65 / 110.0 | 62 / 62 / 0 / 0 | 177 / 177 / 156 / 279 | 196 |
| 200명 6개월 새 가용률 | 60 / 120 / 240초 | −5985 / 69.0 / 170.3 | 51 / 0 / 0 | — / 187 / 281 | 189 |
| 300명 6개월 새 가용률 | 240 / 480초 | −6422 / 250.0 | 56 / 0 | 291 / 411 | 264 |
| **겸직 막음**(`max_concurrent_projects`=1) 100명 6개월 | 30 / 60초 | −4390 / −425 | 31 / 5 | 36 / 111 | **−412**(빈자리 증명) |
| 겸직 막음 100명 12개월 | 30 / 60초 | −9085 | 62 | 62 | −321 |
| 겸직 막음 300명 6개월 | 60 / 120초 | −9257 | 48 | 182 | — |

해석:
- 가용률이 대부분 100%가 되면 **한 사람을 여러 사업에 쪼개 넣는 해**가 폭증한다(100명 안 A 158건, 300명 411건 -- 사용자 기대 "겸직 3%"와 반대). 경우의 수도 늘어 예전 자동 시간 한도(`core/optimize/time_budget.MEASURED` 100명 15초×1.5 = 30초)로는 쓸 만한 해를 못 찾는다.
- 겸직을 막으면 **사업 정원(특히 등급별 자리)이 사람 수에 안 맞아** 빈자리가 증명된다(100명 상한 −412). 생성기 사업 정원은 "월 수요 합 ≤ 공급의 85%"(사람 수 기준)만 맞추고 등급별 공급·겹치는 기간은 보지 않아, 쪼개 넣어야 채워지게 되어 있다.
- 즉 가용률 · 겸직 규칙 · 사업 정원 생성 규칙을 **함께** 다시 맞춰야 한다.

## 부탁(설계부터, 사용자에게 계획 확인 → 구현)
1. **겸직 규칙**: "겸직은 3% 안팎, 하면 두 사업 모두 100%". 대안 예: (a) 겸직자 수 상한 제약(사람별 0/1 변수, 예: ⌈3%·인원⌉) (b) 겸직 감점 (c) 투입률 0/100% 정수화 + 겸직자는 두 사업 예산에 각각 100%.
   모델(`core/optimize/milp.py` -- Codex 영역)·독립 검증기·평가기(`core/evaluate/plan_eval.py`)·Phase 0 오라클·예산 보정(`numerics`)·운영 중 K·보강 계산(`staffing_sim`)이 같은 식을 쓴다(CLAUDE.md "MILP 정식이 두 벌" 함정).
2. **가용률**: 위 가정을 생성기에 넣는다. 참고 구현은 `scripts/make_annual_demo.py`의 `leave_windows`·`available_mm`(같은 시드면 같은 휴직 창, 달력 달 기준이라 6·12개월 묶음이 같은 창을 쓴다). 한 달 휴가는 가용률을 깎지 않고 manifest `leave`에만 남겼다(사용자 "보통 이건 플젝에서 자체 감당").
   주의: 예전 가용률 난수를 그대로 뽑아 버리면 사업 이름·기간·기술 요구가 v2와 같게 남는다(claude-b가 시험해 확인 -- `project_skill_requirements.csv` 해시 동일). 운영 중 묶음은 원래 전원 100%라 생성기 버전 문자열을 올리면 운영 중·연말형 기록의 데이터 버전이 바뀐다.
3. **사업 정원**: 한 사람 한 사업(겸직 3%)으로 등급별로 채울 수 있게(등급별 공급·기간 겹침 고려). 필요하면 사람·사업 데이터 전면 재생성도 사용자 승인됨. 평가 글(reviews·review_items)을 바꾸면 리뷰 판정 LLM을 다시 불러야 한다(`scripts/export_demo_judgments.py`, 외부 LLM은 가상 데이터만) -- 사람·이력·평가 글을 그대로 두면 판정 동봉이 그대로 쓰인다.
4. **시간 한도 재측정**: `core/optimize/time_budget.MEASURED`(10-05 측정)와 claude-b가 넣은 12개월 배수(`api/settings.HORIZON_TIME_FACTOR` = {6: 1, 12: 4}, 100명 실측만)를 새 데이터로 다시 잰다.
5. **다시 만들 것**: `rehearsal.make_demo`(+`make_broken_demo`) → `scripts/make_yearend_demo.py`(연말형, claude-b) → `scripts/make_annual_demo.py`(연간, claude-b -- 원본 org-n100에서 만든다) → `rehearsal.precompute_demo` → `rehearsal.make_demo_records`(org-n100-annual 포함) → 영상 대본·보고서·슬라이드 숫자(D2 57.56/… 등, 벤치·실험 숫자는 예전 데이터 기준임을 밝히거나 다시 잼).
   연간 묶음 도구는 원본의 사업 정원 생성 규칙을 하반기로 옮긴다(`PEAK_CAP` 0.85) -- 생성기 정원 규칙을 바꾸면 이 도구도 같이 바꾼다.
